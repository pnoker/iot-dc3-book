## 2.3 IoT DC3 Microservice Architecture in Practice


> **How to read this section**: IoT DC3 is the open-source engineering reference that runs through this book. Section 2.3.1 presents the overall architecture and collaboration logic of the five centers — the core content for understanding "how an IoT platform implements the five-layer model." Sections 2.3.2 through 2.3.6 expand on each center at the architecture level, focusing on **design decisions and engineering trade-offs** rather than on operating manuals — if you need to build a global picture quickly, reading 2.3.1 and 2.3.7 (the sequence diagram of the collaborative flow) is enough for the chapters that follow. ### 2.3.1 An Introduction to IoT DC3 and the Microservice Philosophy

A car's engine, transmission, and chassis are designed independently, yet they combine into a complete powertrain through standard interfaces. If an IoT platform likewise welds all of its functionality into a single monolithic application, upgrading one alarm rule can drag down the entire data-collection chain. Splitting "collect — unify — analyze — decide — execute — feed back" into multiple microservices that can iterate independently is the core idea of IoT DC3. Understanding its design logic is worth more than memorizing a few service names.

#### Project Positioning: A Universal Foundation, Not a Vertical Product

IoT DC3 is an open-source IoT platform built on a microservice architecture under the Apache-2.0 license. Its goal is not a customized solution for one industry, but a universal foundation spanning the path from device connection to intelligent decision-making. "Universal" means it abstracts the underlying capabilities — device access, unified data, multi-tenant isolation, RBAC (Role-Based Access Control) permissions, time-series storage — without binding itself to any industry logic. "Foundation" means providing a dependable, solid structure — tenant isolation, highly available deployment, horizontal scaling — so that developers need not build this infrastructure from zero. DC3's design philosophy emphasizes microservice decoupling to cope with diverse device access and continuously evolving business logic.

#### Why Microservices: Decoupling Is the First Driving Force

A monolithic architecture works well enough when the device count is small: one device, one driver, one database, all code running in a single process, simple to deploy. But when devices reach the thousands, protocols exceed five, and the rule engine needs weekly updates, the problems surface: changing an alarm threshold requires a full outage; when a time-series write bottleneck appears, the only option is to scale the whole application, dragging the authorization and metadata modules along; swapping the message queue means rewriting the entire data layer.

DC3 splits services along business boundaries; each service deploys and scales independently. The benefits are direct: under heavy write pressure, add instances only to the Data Center; to take on a new protocol, change only the corresponding driver microservice; AI model upgrade experiments never disturb the real-time write channel. The costs are equally clear: service registration and discovery, a configuration center, distributed tracing, transactional consistency guarantees — this extra complexity does not pay off in small environments. DC3 explicitly targets medium-to-large production deployments, where the operational flexibility and development efficiency that decoupling brings far exceed the cost of that complexity.

#### Five Centers: Each Owns a Segment, Together Closing the Loop

Around the closed loop of "collect — unify — analyze — decide — execute — feed back," DC3 carves out five core microservices.

- **Gateway Center**: the system's sole external entry point. It handles route dispatch, token validation, rate limiting, and circuit breaking. It does no business logic — it only does a gateway's proper job.
- **Auth Center**: verifies identity and manages permissions. It implements multi-tenant isolation and RBAC. Its design principle is never to touch device data — even if Auth fails briefly, the data-collection chain keeps running.
- **Manager Center**: a pure metadata service. It manages driver templates, device templates, and point definitions. A point describes one readable/writable variable of a device (such as winding temperature or motor speed); its runtime values flow through the Data Center as point values. This center never touches real-time values — changing an alarm threshold does not disturb the data flow.
- **Data Center**: the data hub. It receives the unified point values reported by drivers, writes them to the time-series database, provides query interfaces, and dispatches control commands. All north-south data exchange must pass through this center.
- **Agentic Center**: the AI capability layer. Built on Spring AI, it integrates large language models (LLMs) and orchestrates Data and Manager APIs through a set of tool-calling interfaces to complete analysis, reasoning, and automated execution. It is the key piece that completes the "understand → decide" loop.

#### Technology Stack and Deployment Constraints

DC3's technology stack centers on the Java/Spring ecosystem: the microservice framework is Spring Cloud + Spring Boot; the API gateway is built on Spring Cloud Gateway with integrated token validation, rate limiting, and circuit breaking; the messaging middleware uses AMQP (Advanced Message Queuing Protocol) to decouple collection from command dispatch; the data layer uses a cache and a time-series database to support metadata and high-frequency writes respectively. The AI layer is implemented with Spring AI, using the tool-calling mechanism to connect to large language models and supporting capabilities such as queries, command dispatch, and alarm analysis.

Even the most minimal runtime requires deploying multiple microservice instances plus supporting middleware — cache, time-series database, and message queue. For medium-to-large production deployments this overhead is entirely acceptable. Orchestrating on Kubernetes additionally requires maintaining service discovery, configuration injection, and log-collection infrastructure, though that cost is usually carried by the cluster as a whole.

#### Engineering Judgment: When to Move to Microservices

The table below lists the typical trade-off points between monolithic and microservice architectures. The numbers are reference thresholds based on common engineering experience, not precise dividing lines; actual decisions must weigh team capability and operational cost.

| Decision factor | Monolith fits better | Microservices fit better |
|:---|:---|:---|
| Number of devices | Few | Many |
| Team size | Small, organized by function | Large, split by business |
| Deployment environment | Single machine or VM | Container-orchestration platform |
| Release frequency | Low, full releases | High, continuous releases |
| Number of device protocols | Limited | Many, diverse protocols |
| AI requirements | None or simple rules | LLM reasoning and tool calling required |

Below those thresholds, the extra operational cost of microservices can slow delivery; past them, the monolith's bottlenecks amplify sharply.

#### Wrapping Up

The Gateway consolidates traffic, Auth governs admission, Manager governs definitions, Data governs flows, Agentic governs reasoning — through the Gateway as the hub, the five centers compose a complete closed loop. Let us now trace how they work together through the full journey of one data collection and one command dispatch.

### 2.3.2 Gateway Center: Unified Entry and Protocol Conversion

> *The following five subsections (2.3.2–2.3.6) are architecture-level walkthroughs focused on design decisions and engineering trade-offs. Source-level implementation details for each center are covered in Chapter 14.*

An industrial site mixes MQTT (Message Queuing Telemetry Transport) temperature-humidity sensors, CoAP (Constrained Application Protocol) smart lighting groups, Modbus RTU relays, and HTTP edge gateways. If every backend service had to face these protocol differences directly, routing and authentication logic would scatter across every corner of the codebase, and maintenance cost and security risk would inevitably climb. The Gateway Center exists to converge these differences into a single unified HTTP/JSON channel at the architectural entry point, so that the downstream Manager, Data, and Agentic centers deal with only one interface specification.

Before getting into the Gateway's design, one key concept: **UAM** (Unified Access Model). Data reported by devices, after being parsed by protocol drivers, is ultimately converted to UAM format, which contains standardized fields such as device identifier, timestamp, and a list of point key-value pairs. What all downstream centers process is UAM-formatted information — not raw Modbus register values or MQTT topic messages.

#### Protocol Conversion: From "Dialects" to a "Common Language"

Upon receiving a protocol request, the Gateway first performs **protocol adaptation**. But the adaptation is not a full protocol-stack implementation inside the Gateway Center — that is the device driver service's job. The Gateway forwards the request to the corresponding device driver service (such as `dc3-driver-mqtt`); after the driver service parses the device instructions of the Modbus, Profibus, or serial protocol, it returns structured point data. The Gateway then performs application-level format normalization on this data, wraps it into a UAM-formatted JSON message, and forwards it to the Data Center or the Manager Center. This two-stage design strips transport-layer protocol detail out of the gateway core, letting driver services iterate independently and hot-plug — instead of modifying gateway code for every new protocol.

To support the normalization process, the Gateway maintains a **protocol adapter registry**. The registry holds three kinds of core information:

- **Protocol type**: MQTT, CoAP, HTTP, Modbus TCP, and so on (exposed by the driver service at registration).
- **UAM mapping rules**: define the correspondence between raw point values and UAM model fields. For example, the temperature value `temp_value` is mapped to `payload.values[0].key = "temperature"`, `unit = "℃"`.
- **Route target**: indicates which backend center a normalized UAM message is sent to. For example, device data is usually routed to the Data Center, while device metadata changes are routed to the Manager Center.

The following configuration fragment shows how adapters for different protocols are registered:

```yaml
# Gateway中心 application.yml（非DC3生产配置）
dc3:
  gateway:
    protocol-adapters:
      mqtt:
        type: MQTT
        driver-service: dc3-driver-mqtt
        uam-mapping-class: com.dc3.center.gateway.adapter.MqttUamMapper
        route-target-center: data
      coap:
        type: CoAP
        driver-service: dc3-driver-coap
        route-target-center: data
      modbus-tcp:
        type: MODBUS_TCP
        driver-service: dc3-driver-modbus
        uam-mapping-class: com.dc3.center.gateway.adapter.ModbusUamMapper
        route-target-center: manager
```

Note that `uam-mapping-class` is optional — if a protocol driver already returns data in UAM format, the mapping class can be omitted and the Gateway forwards directly. This design separates protocol handling from business logic: to take on a new protocol (such as AMQP), developers only implement the corresponding driver service and UAM mapping class, then register the adapter in the configuration — no modification to the Gateway Center's existing routing logic is needed.

#### Authentication and Routing: The Gatekeeper and the Signposts

The Gateway processes every incoming request through the following sequence: **parse identity → validate permissions → inject context → dispatch by route**.

1. **Parse identity**: based on the request source, the Gateway extracts the device or user identity from headers, body, or token. For HTTP requests, a JWT (JSON Web Token) is usually carried in the `Authorization` header. For MQTT/CoAP requests, identity is usually embedded in the Topic or URI.
2. **Validate permissions**: the Gateway itself stores no user or device credentials. It forwards these identity markers to the Auth Center for validation. After verifying the identity, the Auth Center returns an authentication result containing `tenantId` and `role`.
3. **Inject context**: if authentication succeeds, the Gateway uses `TenantContextFilter` to inject `tenantId` into the request's HTTP Header (for example `x-dc3-tenant-id`). This guarantees that every downstream service can enforce data isolation based on that tenant context.
4. **Dispatch by route**: the Gateway dispatches the tenant-tagged request to the corresponding backend center according to the request path. Based on Spring Cloud Gateway's `routes` configuration, a path-mapping example:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: data_route
          uri: lb://dc3-center-data
          predicates:
            - Path=/api/v3/data/**
          filters:
            - name: AuthenticationFilter
          metadata:
            excludeAuthentication: false
        - id: health_check
          uri: lb://dc3-center-data
          predicates:
            - Path=/actuator/health
          filters: []
          metadata:
            excludeAuthentication: true
        - id: manager_route
          uri: lb://dc3-center-manager
          predicates:
            - Path=/api/v3/manager/**
          filters:
            - name: AuthenticationFilter
```

The `uri: lb://` prefix indicates load balancing through a service-discovery component such as Nacos. When the Data Center runs multiple instances, requests are distributed evenly. The `excludeAuthentication` metadata lets paths such as health checks skip authentication, avoiding unnecessary overhead. In practice, watch the ordering of route configuration: Spring Cloud Gateway matches routes in file definition order. If a wildcard path (such as `/api/v3/**`) is placed before a specific path, it can intercept every request. DC3's practice is specific paths first, wildcard paths last.

#### Traffic Control and Security Protection: Rate Limiting and the Firewall

As the service entry point, the Gateway must be able to prevent its resources from being exhausted accidentally or maliciously. Common engineering measures include:

- **Request rate limiting**: based on a token-bucket algorithm or a sliding window, each tenant gets a per-unit-time request ceiling. When one tenant's device reporting frequency spikes, `RateLimitFilter` computes that the request count in the current time window has exceeded the threshold and returns `429 Too Many Requests`, carrying a `Retry-After` header that tells the client to retry later — preventing a total collapse of the backend services.
- **Request body size limits**: set a reasonable ceiling on `Content-Length`; above the threshold the Gateway returns `413 Payload Too Large` directly. The exact value depends on the business — device telemetry is usually small (a few KB), but profile synchronization or firmware upgrades can reach tens of MB, so paths such as `/api/v3/manager/**` need separately raised limits.
- **Path whitelist and parameter validation**: the Gateway maintains a set of allowed target paths. Any request whose target path is not on the whitelist (for example sensitive endpoints under `/actuator`, or internal paths like `/internal/**`) is rejected outright. This filtering happens before route matching. At the same time, request parameters are format-validated, and requests containing illegal characters (such as SQL-injection fragments) are rejected.

These defenses do not amount to absolute security, but at very low performance cost they filter out the vast majority of traffic-pattern attacks. Finer-grained device-level authentication relies on secondary validation by the Auth Center and the Manager Center.

#### Engineering Practice: A Gateway Configuration Checklist

Before onboarding a new device type or releasing a new version, confirming the following points reduces failures caused by routing problems:

1. Is the UAM mapping for the new device protocol registered in the `protocol-adapters` configuration? Is the corresponding `driver-service` registered with the service-discovery center?
2. Does the new feature's route add its `id` in `spring.cloud.gateway.routes`, and does its `predicates` `Path` pattern avoid overlapping existing routes through ordering?
3. Are the authentication and authorization rules explicit? Should the newly created paths be excluded from authentication (such as health checks and static resources)? If so, set `excludeAuthentication: true`.
4. Does the new feature have special request-body size requirements? If they exceed the general limit, consider raising the limit via the `RequestSize` filter, or validating early at the upstream CDN layer.
5. During testing, use `curl --path-as-is` to verify that specific paths are dispatched as expected and that wildcards are not matched incorrectly.

The Gateway Center isolates device-protocol complexity outside the entry point; the Auth Center then guarantees that every interaction has a legitimate identity. Let us analyze the design logic of the Auth and Manager centers and see how permissions and metadata land at the platform layer.

### 2.3.3 Auth Center: Identity Authentication and Permission Management

An industrial IoT platform faces an intricate daily mix of device types, user roles, and data flows. An operator at the console modifies a variable; an automated device reports temperature data through the gateway; a third-party analytics system requests historical points — these actions come from different sources, access different resources, and carry different security levels. Without a unified authentication and authorization layer, permission-checking logic scatters across the Manager, Data, and Agentic centers, multi-tenant isolation depends almost entirely on developers' "self-discipline," and tracing an incident becomes extremely hard. The design goal of the Auth Center (`dc3-center-auth`) is to peel this cross-cutting concern — authentication and authorization — out of business logic, achieving unified authentication, centralized authorization, and tenant isolation. Before a request enters the business core, the Auth Center first answers three questions: who you are, what you can do, and which tenant you belong to.

**Authentication: JWT Combined with OAuth 2.0**

The core credential the Auth Center issues is the JWT. A user or device presents its credentials (username and password, or device keys) in an authentication request to the Auth Center; once validation passes, the Auth Center signs and issues a JWT. The token encapsulates claims such as user identity, role, tenant ID, and token validity period. From then on, every HTTP request from that user or device carries the token in its Header; the Gateway Center can verify the signature directly before forwarding, with no per-request round trip into the Auth Center's server-side storage.

This scheme brings two practical benefits in IoT settings. First, devices and gateways often live with network jitter or intermittent offline periods. If every request had to query a server-side session table, then the moment Redis became unreachable or the database connection pool ran dry, validation failures would reject legitimate requests outright. JWT's self-contained nature avoids exactly this problem — once the Gateway verifies the signature it can read the claims, with no additional network I/O. Second, in a microservice architecture, a centralized session would force the Auth Center to share one session store with the Manager, Data, and other centers (or reach a global Redis through consistent hashing), introducing a centralized single-point bottleneck and its maintenance cost. JWT distributes the state into the token itself; business centers only need the public key to verify signatures, squeezing the authentication overhead of cross-center calls to a minimum.

JWT carries a cost that cannot be dodged: once issued, the server cannot actively revoke the token. The common engineering answer is a short access_token validity period (usually configured around 15 minutes, with the exact value set by operations policy) plus a refresh token that lets users renew silently after expiry. On refresh, the Auth Center re-checks the user's status — if the account has been disabled, the refresh request is rejected — which effectively achieves near-real-time token invalidation.

For third-party application integration (for example an external AI agent reading device point data through MCP (Model Context Protocol) interfaces), the Auth Center also implements the OAuth 2.0 (Open Authorization 2.0) authorization-code flow. The user is redirected in the browser to the Auth Center's authorization page; after the user confirms, the Auth Center issues an authorization code to the third-party application, which exchanges it for an access_token. The combination of OAuth 2.0 and JWT forms the complete chain of "who authenticates, who authorizes," covering all three identity scenarios: people, devices, and third-party systems.

**The Permission Model: RBAC and Tenant Isolation**

After authentication comes authorization. At the authorization layer, DC3's Auth Center chose the RBAC model. Every user is assigned one or more roles, and every role binds a set of permissions. Permissions are expressed as `resource:action`, for example `device:read`, `command:write`. Operators need not configure fine-grained permissions user by user; they manage in bulk through roles, which markedly lowers the configuration and maintenance cost of permissions in large-scale deployments.

RBAC answers only "may this be done"; it does not answer "for whose data." IoT platforms are almost universally multi-tenant — one platform operator may serve several factories or parks at once, and one factory's operators must never see another factory's device points. DC3 therefore layers tenant isolation on top of RBAC: the tenant ID a user belongs to directly bounds the data scope the user can see. When the Data Center writes a point value, it attaches the tenant label at the same time; when the Auth Center validates permissions, it first confirms the user's role carries the required operation permission, then confirms that the requested resource belongs to the user's tenant. This pair of filters — roles deciding "may it be done," tenants deciding "for whose data" — is a common and effective engineering practice for security isolation in multi-tenant IoT platforms.

In implementation, the Auth Center maintains a set of relation tables storing the mappings among roles, permissions, and tenants. The Manager Center provides the UI for managing this metadata — creating roles, assigning users, and configuring permissions are done through Manager's screens, but the management interfaces and storage for this data ultimately live in the Auth Center. Manager never touches authentication logic; it is responsible only for reading and writing the metadata.

**Unified Authentication for Devices and Users**

User logins use username and password — but what do devices use for access? When each device registers, the Manager Center generates a pair of device keys (AccessKey / SecretKey). When the device reports data through a driver, it first makes a special authentication request at the Gateway layer; after the Auth Center validates the keys, it signs a JWT carrying the device's identity. That token is attached to the header of every point-value message the device reports, ensuring the data source is trusted and traceable. Devices and users have their identities managed by the same Auth Center, but with different credentials — users use passwords, devices use keys. Whether an operation comes from a person or a report from a machine, the security audit log can trace it back to a concrete identity.

Device tokens usually live much longer than user tokens, but at issuance the Auth Center additionally binds a "device fingerprint," such as the device MAC address or the driver instance ID. If the Gateway notices, while forwarding, that the fingerprint declared in the token does not match the network identity of the actual request source, it can reject the token outright, further reducing the risk after a key leak.

**How Auth Cooperates with the Other Centers**

The Auth Center does not stand alone. Its cooperation pattern with the other four centers can be summarized as: **the Gateway checks tickets, Auth issues them, Manager administers permissions, and Data/Agentic do not re-check at execution time**.

- **With Gateway**: for every request it receives, the Gateway calls the Auth Center's interface to verify the JWT. If the token has expired or permissions are insufficient, the Gateway returns 401/403 directly and the request never reaches the business layer.
- **With Manager**: Manager provides editing screens for roles, permissions, and tenants; these changes are written through APIs into the Auth Center's database. Manager neither authenticates nor governs permissions.
- **With Data / Agentic**: the Data Center and the Agentic Center must also carry JWTs on RPC calls between internal microservices. Although these are intranet communications, DC3's design principle is that all cross-center calls must pass Auth validation, to prevent horizontal privilege escalation.

This cooperation yields two engineering gains. First, permission logic does not scatter — each business center cares only about "how to do it," not "who is doing it." Second, security policy upgrades in one place — if the token format or the underlying cryptography later needs to change, only the Auth Center changes, and every other center adapts automatically.

**A Security Best-Practices Checklist**

From the Auth Center's architecture, a security checklist for the deployment and operations stages helps teams quickly identify common vulnerabilities:

1. **Token hardening**: give the access_token a short validity period (commonly around 15 minutes) and pair it with a refresh_token for silent renewal; the Auth Center should store the hash of the refresh_token, so it can be forcibly invalidated when the user logs out or the account behaves abnormally.
2. **Transport security**: force HTTPS on every interface that carries a JWT; when the Gateway forwards to intranet centers, mTLS (mutual TLS) is likewise recommended, to prevent token leaks through intranet sniffing.
3. **Least privilege**: when assigning roles to devices and third-party applications, follow the principle of least privilege — a temperature-humidity sensor that only reports data should have a role containing only `data:write`, never `device:read` or `command:write`.
4. **Audit logging**: the Auth Center must record every authentication success, failure, and permission denial. Log fields should include at least source IP, operation time, user/device ID, and the requested resource and action. These logs are the key evidence for after-the-fact security audit and traceability.

Auth does not process business data directly — it stores no device points, runs no rule engine, hosts no large model. Yet it is the foundation of all security in the architecture. Without it, the Gateway is just an open door, multi-tenant isolation exists in name only, and the risks of data leakage and privilege escalation climb sharply. ### 2.3.4 Manager Center: Device Management and the Rule Engine

In IoT DC3's five-center architecture, the Manager Center (`dc3-center-manager`) plays the configuration-driven hub role. It does not handle device data flows directly — that is the Data Center's and the Gateway Center's job — it manages all device metadata and business rules. Managing devices, defining rules, and configuring scenes is its core mission. Upper-layer applications (including the Agentic Center) obtain device inventories, point definitions, and rule configurations through the Manager Center; the lower-layer Gateway and Data Centers execute data collection and command forwarding according to that configuration.

#### Device Registration, Grouping, and Lifecycle Management

The core object the Manager Center manages is the device's digital mapping in the platform. This mapping contains metadata such as device identity, model, point list, communication protocol, registration location, and owning tenant, stored in a relational database.

Device registration proceeds in two steps. In the first, an operator creates a device instance on the management screen and specifies the driver template it belongs to. A driver template defines the communication protocol and point structure for a class of devices — for example, a "temperature-humidity sensor template" declares two points, `temperature` and `humidity`, each with a data type and unit. In the second, the Manager Center generates a device secret for the instance, which the Auth Center later uses for the device's identity authentication.

At large scale, grouping is more efficient than managing devices one by one. The Manager Center supports multi-level grouping:

- **Tenant-level grouping**: isolated along organizational boundaries; devices of different tenants are naturally invisible to each other.
- **Site-level grouping**: for example "Workshop 1," "Warehouse 2," "Office Building Floor 3."
- **Function-level grouping**: for example "temperature sensors," "air-conditioning actuators," "security door controls."

Groups can nest: one site-level group contains several function-level groups. Rules, data queries, and alarm policies can all be applied in bulk by group. A "Workshop 1 humidity alarm" rule only needs to be attached to that group, and newly added temperature-humidity sensors fall under the rule's coverage automatically.

Device lifecycle management tracks the full path from registration to retirement. The Manager Center maintains a state machine for each device, with typical states including: not activated, online, offline, under maintenance, and deregistered. State changes trigger corresponding events. For example, when a device stays "offline" longer than the threshold after being "online," the Manager Center pushes an alarm notification. This state machine gives the platform precise control over device status and is also an important source of input events for the rule engine.

#### The Rule Engine's ECA Model: Event, Condition, Action

Device management is the foundation. The Manager Center's real value lies in its embedded rule engine, whose core is the Event-Condition-Action (ECA) model:

- **Event**: may be the arrival of real-time data (for example a temperature point-value report), a device state change (online/offline), a timer expiring, or an external API call.
- **Condition**: a boolean expression evaluated against the event data. Common conditions include numeric comparison (`pointValue > threshold`), string matching, time-range checks, and compound conditions (meeting threshold 1 or threshold 2). Conditions support AND, OR, and NOT combinations.
- **Action**: the operation executed once conditions are met. Typical actions include sending a command to a device, pushing an alarm to notification channels (email, SMS, WeChat), calling an external Webhook, storing an inference result, or triggering another rule to form a cascade.

Consider one scenario: a warehouse with several temperature sensors installed. An operator configures a rule; the rule's JSON configuration is as follows (illustrative only, not DC3's actual format):

```json
{
  "ruleId": "rule-temp-alert-001",
  "name": "仓库温度超标告警",
  "enabled": true,
  "trigger": {
    "type": "point_report",
    "deviceGroupIds": ["group-warehouse-sensors"],
    "pointCode": "temperature"
  },
  "conditions": [
    {
      "id": "cond-yellow",
      "expression": "pointValue > 阈值1 && pointValue < 阈值2",
      "priority": "YELLOW",
      "actions": [
        {
          "type": "alert",
          "level": "yellow",
          "message": "设备{deviceId}温度{pointValue}°C，超黄牌阈值",
          "channels": ["email", "sms"]
        }
      ]
    },
    {
      "id": "cond-red",
      "expression": "pointValue >= 阈值2",
      "priority": "RED",
      "actions": [
        {
          "type": "alert",
          "level": "red",
          "message": "设备{deviceId}温度{pointValue}°C，严重超限！",
          "channels": ["email", "sms", "wechat"]
        },
        {
          "type": "command",
          "deviceIds": ["device-fan-a", "device-fan-b"],
          "pointCode": "fan_speed",
          "value": 100
        }
      ]
    }
  ]
}
```

The rule engine never talks to hardware directly. Once it evaluates the conditions, it wraps the command action in a standard format and sends it to the driver through the Data Center's message queue; the driver performs the write and the device returns an acknowledgement — this is the concrete implementation of the "collect → evaluate → execute" loop. For more discussion of the data-chain loop, see the data-pipeline and stream-processing material in Chapter 5.

#### Scene Linkage and the Visual Interface

A single rule handles a single triggered action. In engineering practice, many scenes require multiple devices to coordinate in sequence, or one state change to set off a chain of dependent actions. The Manager Center supports this multi-step orchestration through "scene linkage" — a lightweight workflow engine. It lets you define one triggering event, a set of preconditions (such as a time window), and a list of actions executed sequentially or in parallel. Each action can carry a delay, and actions can share context variables — the return value of one command can serve as the input parameter of the next. An industrial example: when temperature exceeds the limit, first start the exhaust fans, start the air conditioning after a 5-second delay, and raise a full alarm if the temperature has not dropped after 30 seconds. Scene linkage extends the rule engine from single trigger points to multi-step orchestration, and is the key to "unattended" automation.

The Manager Center's visual interface lets operators configure trigger events, conditions, and actions by dragging nodes, without editing JSON by hand. The interface turns both the rule engine's ECA model and scene linkage's orchestration logic into visible graphs; every step can be previewed and tested, lowering the technical barrier for operators.

#### Architectural Lesson: The Design Trade-off in Data Consistency

An architectural question worth pondering: why put the rule engine inside the Manager Center instead of making it a standalone service? The trade-off lies between coupling and data consistency. When a device is deregistered in the Manager Center, a standalone rule engine would need an extra message telling it to stop the related rules — a lost or mis-ordered message could send commands to a deregistered device. Placing the rule engine and metadata management in the same microservice, sharing the same transactional boundary and database, keeps rule state and device state consistent at all times. The cost is a heavier responsibility for the Manager Center, whose code modules must be strictly layered to keep business logic from tangling. For most IoT projects the trade-off is sound — a wrong rule does more harm than a slow one.

**Practice Checklist: Manager Center Configuration**

1. **Device registration phase**: confirm the driver template has been created and point definitions are correct (data type, unit, read/write attributes). Record the device secret at creation and deliver it securely to field installers.
2. **Grouping strategy**: split by site first, then by function. Avoid letting a single group hold too many devices — the cost of resource queries grows linearly with group size.
3. **Rule testing**: before going to production, run the rule with a test device and watch the log output. Pay special attention to boundary values in compound conditions (for example, whether "reaching the threshold" includes the boundary).
4. **Scene linkage debugging**: set reasonable delays between steps. Too fast can pile up processing on the device side; too slow can miss timeliness requirements.
5. **Lifecycle cleanup**: periodically inspect "deregistered" devices and archive their historical data in the time-series database, reducing metadata redundancy in the relational database.

### 2.3.5 Data Center: Data Collection, Storage, and Distribution

Once device data reaches the platform, who receives it? The Manager Center manages devices and defines rules but stores no data; the Auth Center governs authorization and never touches data. The one that actually catches the "stream of point values" collected from devices, stores it well, and distributes it is the **Data Center** (`dc3-center-data`).

The Data Center is the core of IoT DC3's data pipeline. It receives the southbound drivers' collection results from the Gateway, writes these semantically tagged, structured `PointValue` records into time-series storage, and simultaneously pushes them to subscribers through the message queue — perhaps a real-time monitoring dashboard, the rule engine, or an Agentic Center in the middle of analysis and inference. In one sentence: **receive data, clean data, store data, distribute data**.

#### Receiving Data from the Gateway: Buffering and Decoupling

The path of device-reported data: a driver `dc3-driver-*` reads the raw signals of field devices (PLCs, power meters, sensors), normalizes them into `PointValue`, and sends them to the Gateway via MQTT or a direct HTTP POST. After routing and authorization, the Gateway forwards the data to the Data Center.

The Data Center's first move is not to store but to **buffer**. Under high concurrency, writing straight into the database becomes the bottleneck. DC3's approach is to place a message queue between the Data Center and storage — RabbitMQ as the buffering layer. Data first goes into a specific RabbitMQ exchange, and consumers write it into the database asynchronously. This design brings two benefits:

- **Peak shaving**: transient reporting peaks (such as every building reporting on the hour) are absorbed by the queue, and the database always writes at a steady rate.
- **Decoupling producers from consumers**: write speed and consume speed no longer depend on each other. If the Agentic Center is busy with long-running inference, no data is lost — the queue holds it for later consumption.

This "receive once, distribute twice" pattern satisfies both durability and real-time requirements.

#### Data Cleansing and Preprocessing

Before data enters the queue, the Data Center also handles cleansing and preprocessing. The raw `PointValue` reported by a device may carry the following quality problems:

- **Timestamp anomalies**: device clock drift can throw timestamps into the future or the past; the Data Center verifies that the timestamp falls within a reasonable window (for example, no more than ±5 minutes from the current time) and drops the record or flags it as anomalous beyond that.
- **Out-of-range values**: values clearly impossible physically are rejected according to the measurement range defined in the point template (for example, temperature confined to -40 °C to 150 °C).
- **Unknown points**: if the reported point ID is not registered in the Manager Center, the Data Center simply ignores the point value.
- **Duplicate data**: after a device reconnects it may resend earlier samples; the Data Center deduplicates through a unique index of "device + point + timestamp."

Only the cleansed data enters the queue. This step keeps dirty data from contaminating the time-series store and lightens the processing load on downstream consumers. Preprocessing also includes unit standardization: some sensors report temperature in Fahrenheit, and the Data Center converts everything to Celsius before storage.

#### Data Storage: Choosing and Weighing a Time-Series Database

The most representative characteristic of IoT data is **a continuously produced stream of timestamped values** (time-series data). Relational databases (such as MySQL) store time-series data inefficiently: single-table row counts balloon rapidly, range-query performance degrades sharply, and automatic cleanup is awkward. Industrial-grade IoT platforms therefore almost universally adopt a time-series database.

DC3's choice is **TimescaleDB**. TimescaleDB is a time-series extension of PostgreSQL: it inherits PG's SQL capabilities and mature ecosystem while adding automatic partitioning, compression, and retention policies for time-series data. The engineering trade-offs behind this choice deserve a closer look:

- **Why not InfluxDB?** InfluxDB is known for high write performance and its native query language, but it uses a homegrown storage engine and needs extra adaptation to fit an existing Java stack. DC3's admin console and metadata already run on PostgreSQL; adopting TimescaleDB only adds an extension, with no second database system to maintain.
- **Why not Elasticsearch?** Elasticsearch excels at full-text search, but as a time-series store it needs extra index tuning, has a large memory footprint, and is not natively aimed at time-series workloads. TimescaleDB directly provides hypertable creation, automatic partitioning, and columnar compression.

Choosing TimescaleDB is, in substance, the engineering practice of **merging into the existing technology stack**. The design philosophy of "covering the broadest functionality with the fewest database systems" runs through all of DC3: authorization, metadata, and time-series data are all carried by the PG/TimescaleDB family, reducing operational complexity.

The `PointValue` structure stored in TimescaleDB is as follows (not a complete DDL statement — it only sketches the core field design):

```sql
-- 例子：DC3 位号值存储的核心字段
CREATE TABLE point_values (
    time        TIMESTAMPTZ       NOT NULL,     -- 采样时间点
    device_id   VARCHAR(64)       NOT NULL,     -- 设备ID
    point_id    VARCHAR(64)       NOT NULL,     -- 位号ID（如“温度_01”）
    value       DOUBLE PRECISION,               -- 数值
    text_value  TEXT,                           -- 字符串值（位号类型不同时使用）
    unit        VARCHAR(16),                    -- 单位，如℃、kPa、V
    tenant_id   VARCHAR(32)       NOT NULL      -- 租户ID，用于多租户数据隔离
);

-- 按时间和设备创建超表与索引
SELECT create_hypertable('point_values', 'time');
CREATE INDEX idx_device_time ON point_values (device_id, time DESC);
```

Every record carries tenant context, ensuring data isolation in multi-tenant scenarios.

#### Data Distribution and Historical Queries

Writing to the time-series store is not the end. Once data lands, the most pressing need is **to be consumed**. The Agentic Center's inference engine needs live data to judge device status; the alarm rule engine needs the latest values to trigger alerts; real-time dashboards need continuously refreshed charts. These consumption scenarios differ in their latency requirements:

- **The Agentic Center**: reads historical data for analysis and is latency-insensitive; it queries TimescaleDB directly, and minute-level responses suit it.
- **Real-time monitoring** (such as a WebSocket-driven front-end dashboard): needs second-level refresh; subscribing directly to the latest `PointValue` from the message queue suffices.
- **The alarm rule engine**: triggered by rules configured in the Manager Center; the Data Center forwards data to the alarm service for state-machine evaluation.

On receiving data, DC3's Data Center writes it to the message queue and the time-series store at the same time. Message-queue consumers subscribe to the data streams of specific devices or points as their needs require, avoiding the waste of "every consumer type querying the database in turn." This pattern — **one store write and one stream push at write time** — is a common design in IoT data pipelines.

For historical queries, the Data Center exposes a REST interface supporting time ranges, point filters, and aggregation functions. For example, to query a device's maximum, average, and minimum temperature over the past hour, the interface path looks roughly like:

```
GET /data/history/{deviceId}/{pointId}?start=2025-03-01T00:00:00Z&end=2025-03-01T01:00:00Z&aggregate=avg,max,min&interval=5m
```

It returns a JSON array in which each record contains a timestamp and aggregated values. Under the hood the Data Center uses TimescaleDB's `time_bucket` function for downsampled aggregation — no complex custom logic required.

#### Time-Series Compression and Retention Policies

Time-series data grows fast. A smart factory with 10,000 points sampling every 5 seconds produces an astronomically large number of records per day (as an example). Without a retention policy, storage cost runs out of control.

TimescaleDB provides built-in compression and retention policies. DC3's typical configuration is a tiered storage strategy (specific retention periods are decided by business needs):

| Data tier | Content stored | Retention period | Compression method | Estimated compression ratio |
|---------|---------|---------|---------|-----------------|
| Hot data (raw) | Raw `PointValue` records | 7-30 days | TimescaleDB columnar compression | Substantially lower disk usage |
| Warm data (downsampled) | Minute-level aggregates (mean, max, min) | 1-6 months | Columnar compression | Significant space savings |
| Cold data (long-term archive) | Hourly/daily aggregates | 1-3 years | Cold-storage archiving (e.g., S3) | N/A |

**Table 2-1** Tiered data-retention strategy

- **Raw data retention**: production sites usually keep 7 days, labs or test environments 30 days. Beyond that, data is automatically deleted or downsampled.
- **Automatic downsampling**: raw data past its retention period is aggregated into minute-level or hour-level records (max, min, mean) and stored in downsampled tables.
- **Data compression**: raw data is compressed with columnar storage. TimescaleDB's columnar compression can greatly reduce disk usage.

Downsampled aggregate data is retained much longer (for example 1 year), supporting long-term trend analysis and report generation. This tiered strategy — "hot data stored and queried fast, cold data compressed and archived" — is the standard answer to the flood of time-series data in IoT.

#### Example: The Data Center's Write Interface

The Data Center exposes a REST interface to receive the `PointValue` records forwarded by the Gateway. Here is an interface definition (in Spring Boot framework style):

```java
// 例子：DC3 Data中心接收数据的 REST 控制器
@RestController
@RequestMapping("/data")
public class DataController {

    @PostMapping("/pointValues")
    public ResponseEntity<Void> receivePointValues(
            @RequestBody List<PointValue> values) {
        // 1. 将数据写入 RabbitMQ 队列，指定路由键为 "dc3.data.point"
        rabbitTemplate.convertAndSend("dc3.data.point", values);
        // 2. 直接返回 202 Accepted, 表示已接收、待异步处理
        return ResponseEntity.accepted().build();
    }
}

// 位号值模型（简化版）
public class PointValue {
    private String deviceId;       // 设备ID
    private String pointId;        // 位号ID（如“温度_01”）
    private double value;          // 数值
    private String textValue;      // 字符串值（位号类型为字符串时使用）
    private String unit;           // 单位，如℃
    private Instant time;          // 数据采样时间戳
    private String tenantId;       // 租户ID，用于数据隔离
}
```

Note that the interface returns `202 Accepted`, not `200 OK`. This means the Data Center only confirms "received and queued," not "written to the database." Final confirmation of the write happens asynchronously on the consumer side. The design decouples response time from write latency, avoiding the timeout risk of the device waiting for the database write to finish — during reporting peaks, network latency competing with database writes could otherwise time out on the device side and trigger retries, introducing needless duplicates.

#### Practical Takeaways

1. **Choose the right time-series database**. DC3's choice of TimescaleDB is an engineering judgment about integrating with the existing PG ecosystem. Teams fluent in InfluxDB or Elasticsearch can substitute them, but must weigh integration cost and operational overhead.
2. **Design a sound retention policy**. A time-series store without one will lose control of both query performance and storage cost after running for a while. Start from business needs to define the hot-data retention period, then enable automatic downsampling and cleanup.
3. **Attend to data cleansing up front**. Once dirty data enters the time-series store it is hard to clean retroactively; filter it with validation rules before storage. Common quality problems include timestamp anomalies, out-of-range values, and unregistered points.
4. **Exploit the message queue's buffering**. Do not write data straight into the database; pass it through a message queue first to shave peaks and fill valleys. The queue also decouples writing from consumption and raises overall system availability.
5. **Design a unified query interface**. The historical query interface should support time ranges, point filters, and aggregation functions. Using the time-series database's native aggregation (such as TimescaleDB's `time_bucket`) can markedly simplify the implementation.

### 2.3.6 Agentic Center: The Hub of Intelligent Decision and Execution

The Data Center has caught the device data, stored it, and distributed it. Now return to the question raised in Section 2.1: who "decides"? Who turns data into actions?

In the classic four-layer architecture, this step falls either to people — an operator watching the monitoring wall and clicking "open valve" by hand — or to static rules — "if temperature exceeds 30 °C, turn on the air conditioning," hard-coded in the program. Both approaches strain against dynamic, complex scenes. IoT DC3's answer is the **Agentic Center** (`dc3-center-agentic`), which turns the intelligence layer from a concept into a running microservice.

The Agentic Center is the engineering realization of the "intelligence layer" described in Section 2.1.2. Its duties go beyond "analyzing data": it takes on the three **reasoning, planning, and execution** stages of the closed loop. This center is not a simple rule engine but a hub where the LLM participates directly in operational decisions.

#### Core Capability: From "Watching Data" to "Moving Devices"

The Agentic Center's kernel is the **Spring AI** framework, which provides the tool-calling mechanism. Put simply, the LLM gets a "toolbox" — each tool is a Java method annotated with `@Tool`, corresponding to one platform operation, such as "query a device's current temperature," "write a point value," or "send a command to a device." On receiving a user instruction, the LLM decides for itself which tool to call and with what parameters, then returns the result to the user or triggers the next action. The mechanism is compatible with the OpenAI API standard, so mainstream models such as GPT, Claude, and DeepSeek can all be plugged in.

This mechanism gives the Agentic Center three key capabilities:

1. **Semantic understanding and reasoning**: users need not remember device IDs or point codes; they can simply say "is the motor temperature on production line 3 running high?" The Agentic Center parses the semantics, correlates metadata, calls the query tools, and delivers an analysis with context.
2. **Multi-step planning**: a single query can set off a chain of operations. For "bring the workshop temperature down to 22 °C," Agentic first queries the current temperature, compares it with the target value, then decides whether to open the chilled-water valve wider or lower the fan frequency, and finally issues several commands.
3. **Confirmation for high-risk actions**: not every command executes directly. The Agentic Center grades risk: read operations pass automatically, while write operations (especially parameter changes and device start/stop) pop up a second confirmation dialog on the interaction interface, requiring operator review before execution.

Below is pseudocode of the Agentic Center handling a user instruction. This is not DC3 source code, but it summarizes the working logic.

```text
// Agentic 执行决策伪代码
// 例子：用户发指令“把A楼空调温度调到24度”

function handle_user_intent(intent: "把A楼空调温度调到24度"):
    // 1. 解析意图，提取实体：设备位置=A楼，设备类型=空调，目标温度=24
    entity = llm_parse(intent)

    // 2. 查询设备元数据（调用 Manager 中心 API）
    device_info = api_call("query_device", {
        "location": entity.location,
        "type": entity.device_type
    })
    // 返回：设备ID="AC_001", 当前位号值=temp, 位号ID="temp_setpoint"

    // 3. 查询当前温度（调用 Data 中心 API）
    current_temp = api_call("query_point_value", {
        "device_id": device_info.id,
        "point_id": "temp"
    })

    // 4. 规划动作：计算温差，决定需要调低多少度
    delta = entity.target_temp - current_temp  // 假设 delta = -2

    // 5. 风险判断：写操作，需要确认
    if risk_level("write") == "high":
        user_confirm("将 A楼空调 设定温度由 " + current_temp + " 改为 " + entity.target_temp)
        if not confirmed:
            return "操作已取消"

    // 6. 执行：调用工具，写入位号值
    result = tool_call("write_point_value", {
        "device_id": device_info.id,
        "point_id": "temp_setpoint",
        "value": entity.target_temp
    })

    // 7. 反馈：将结果返回给用户
    return "A楼空调温度已设置为 " + entity.target_temp + "°C"
```

The pseudocode shows how the Agentic Center chains the Data Center (query current values) and the Manager Center (query device metadata), and finally issues commands to the device through the gateway. Every step stays inside the closed loop, with no interruption while a human switches tools.

#### Interacting with the Data Center: Data Feeds Decisions

The Agentic Center is no island. To read data, it must bind tightly to the Data Center. Their interaction concentrates on two scenarios:

- **Real-time inference**: Agentic needs the device's most recently reported value — is it 25.3 °C or 80.5 kW? These data are read straight from the Data Center's time-series cache, with millisecond-level response and no impact on write throughput.
- **Historical trends**: some judgments need context. For "has the motor temperature been creeping up over the last two hours?" the Agentic Center asks the Data Center for the most recent N historical points, then lets the LLM decide whether an anomalous pattern exists.

Look back at the closed-loop diagram in Section 2.1.2: from "collect → store" to "understand → decide → execute," the Agentic Center is the bridge connecting the "store" node to the "execute" node. It is not responsible for long-term storage — that is the Data Center's business — but all real-time and near-real-time data movement passes through it.

#### Example: Automated Greenhouse Environment Control

The following example walks through the Agentic Center's full operating flow. The scene is a smart greenhouse managed by the IoT DC3 platform.

**Background**: the greenhouse grows a batch of crops sensitive to temperature and humidity. The Manager Center has created device templates, registered temperature-humidity sensors, grow lights, and ventilation fans, and defined the points. The Agentic Center is configured to connect to an open-source LLM.

**Trigger**: at 3 a.m., the outdoor temperature plummets. Sensor-reported data flows through the Gateway → Data Center into the database. At this point a periodic inspection task deployed in the Agentic Center (triggered by the Spring scheduler) starts and issues an instruction to the LLM: "Check the current greenhouse environment state; if there is a problem, propose and execute an adjustment plan."

The Agentic Center's reasoning flow (this book's example scene; the values illustrate engineering judgment and are not general statistical conclusions):
1. **Query state**: via `@Tool`, call the Data Center's interface to fetch the current sensor point values. The result: temperature 12 °C (threshold lower bound 15 °C), humidity 80% (normal range 60-85%).
2. **Identify the problem**: the LLM analyzes the data and identifies that the temperature is below the set threshold — a "low temperature" alarm.
3. **Plan the response**: the LLM searches the tool list for available actions. It finds a "start grow-light heating" tool for this greenhouse, and a "close ventilation fan" tool. The LLM decides the execution steps on its own: ① close the ventilation fan, reducing cold-air exchange; ② start the grow lights in heating mode.
4. **Execute**: call the two write-point tools in turn, dispatching commands through the Gateway to the corresponding device drivers. Before each write, the system grades the operation's risk — in greenhouse automatic control, adjusting grow lights is usually classified as "medium risk" and would need confirmation? No — Agentic lets operators configure a whitelist of auto-executed operations. Any device and operation written into the whitelist executes directly, without confirmation.
5. **Feed back and record**: the Agentic Center writes the whole decision process — input data, inference results, executed commands, execution receipts — into the Data Center's operation-log table for after-the-fact audit.

Through all of this, the operator never even woke. The next morning he opens the platform and finds a system message: "At 03:14, as the temperature fell to 12 °C, grow-light heating started automatically; the temperature has recovered to 16 °C."

#### Feedback Mechanism and Self-Optimization

The Agentic Center does not stop at a single execution. It has a feedback loop to improve decision quality. After each execution, the system records the following: did the user accept the decision? Did the execution result meet expectations? If the user manually corrected an Agentic output (for example revoking a command), that correction is marked as a training sample and given priority in later model fine-tuning or rule iteration. The platform also supports exporting execution data over the MCP protocol to external AI agents for offline analysis.

#### Boundaries and Trade-offs

The Agentic Center is not omnipotent. Its design rests on several explicit assumptions:

- **Where it fits**: scenes with complex decision logic that need natural-language interaction or context understanding. Purely deterministic control ("open the relief valve when pressure exceeds 10 MPa") is lighter when left to a rule engine.
- **Latency**: calling an LLM costs network time. End-to-end, one instruction parse and execution — from the user's question to the device's response — typically takes seconds (depending on the model and the network), unsuitable for sub-second control loops.
- **Dependencies**: it depends on the Data Center and the Manager Center, and cannot work independently while the platform is offline.

This design follows the division of labor from Section 2.1.2.1: **train in the cloud, infer at the edge, respond on the device**. The Agentic Center runs in the cloud, carrying out the reasoning and planning that need models and context, while fast responses on the device side are handled by local logic in the device driver or the edge gateway. The two cooperate: real-time performance is not sacrificed, and the flexibility of intelligent decisions is gained.

### 2.3.7 The Five Centers in Concert: The Complete Flow from Device Registration to Intelligent Control

The preceding sections took apart IoT DC3's five centers — Gateway, Auth, Manager, Data, Agentic — each owning one segment of the chain. But an IoT platform's real value lies not in any single center's strength; it lies in how they string together into a complete action loop. A sensor traveling from network access to finally changing an actuator's state must pass through authentication, metadata binding, data normalization, intelligent inference, and command dispatch — miss one link and the loop is broken.

This section threads the five centers' collaboration through one complete device lifecycle — from first registration to intelligent control. What you get is not a concept diagram but an "end-to-end map," so that in later architectural design you know where every message is headed.

#### Process Overview: Managing Devices in a Smart Irrigation System

Imagine a smart greenhouse running IoT DC3, fitted with one soil-moisture sensor and one solenoid valve. The goal: when moisture falls below the threshold, the system opens the valve to water automatically, and closes it once moisture recovers. The whole operation divides into six steps, a relay through the five centers. Each step below flags the key design decisions — when you meet a similar scene, you can match your choices against them directly.

**Step 1: the device registers through the Gateway and authenticates with Auth.**  
Once the device physically powers on, it first sends a registration request to the gateway (`dc3-gateway`). The gateway is the platform's only external HTTP entry (per the IoT DC3 design documents); it handles no business logic, only routing and injecting the authorization context. The gateway passes the registration request (carrying the device's unique identifier and initial token) to the Auth Center (`dc3-center-auth`). The Auth Center verifies the device identity — checking whether the serial number is registered and the token still within its validity — and returns a JWT as the session credential. That JWT is then attached to every data request the device makes. Only devices that pass Auth's authentication are let through by the gateway to the rest of the flow.  
*Design decision*: why not embed authentication logic directly in the Gateway? Because once decoupled, Auth can strengthen authentication independently (for example adding OAuth 2.0 support) without touching the gateway's routing logic, and it fits neatly into unified security auditing.

**Step 2: the Manager Center creates device metadata and rules.**  
Once the device clears authentication, an operator finishes the remaining registration configuration in the Manager Center (`dc3-center-manager`). Manager owns all metadata — driver templates, device types, point definitions. For the soil-moisture sensor, the operator needs to:
- select a driver template (assume a Modbus protocol driver)
- create the device instance, filling in name, serial number, and geographic location
- define the point list: moisture (`humidity`), data type `float`, unit `%`, read range 0–100
- set static rules: trigger conditions judged on moisture trend and duration — for example, a low level triggers opening the valve, a high level triggers closing it

Once configuration is complete, Manager stores the metadata in the database and syncs the rules to the Data Center.

**Step 3: device data goes through the Gateway → Data Center into storage.**  
The device reports soil-moisture values at a preset interval (by way of example). When the data reaches the Gateway, the Gateway takes out the JWT injected earlier and forwards the raw payload to the Data Center (`dc3-center-data`). The Data Center first normalizes: converts raw values into percentages according to the point's measurement range; attaches point semantics, unit, timestamp, and tenant ID to each record, producing the standard `PointValue` structure; then writes to the time-series database; and simultaneously pushes it to the built-in rule engine to check Manager's preset triggers. Suppose the moisture drops to the low level and stays there across several reports — the Data Center's rule engine judges the trigger condition satisfied.

**Step 4: the Agentic Center reads from the Data Center and reasons.**  
The rule is static — below the threshold, open the valve. But more complex scenes need intelligent judgment: is it raining outside? Is the device faulty? How is moisture trending in other zones? This is where the Agentic Center (`dc3-center-agentic`) steps in. Through its configurable tool-calling mechanism, Agentic calls the "query the device's point history for the last hour" tool, obtains the moisture data from Data, feeds it into the loaded LLM, and pulls external weather-API data for a combined judgment. After reasoning, the LLM concludes "the drought trend is clear, no rain forecast, open the valve immediately," which becomes the structured instruction: "write point `valve_state` with value `1` (open), target device: the solenoid valve."

**Step 5: the Agentic Center issues the control command through the Data Center.**  
Agentic never connects to devices directly; it delivers commands via Data. On receipt, Data converts them to the standard command format and sends them to the driver service through the message queue. This abstraction layer decouples AI inference from device execution — Agentic need not care whether the device speaks Modbus or MQTT.

**Step 6: the Gateway forwards the command to the device for execution and receipt.**  
The driver service reads the command from the message queue, converts it into physical-layer signals (for example, writing a coil register over Modbus), and dispatches it to the solenoid valve to open. The execution result (success/failure) returns along the same path: driver → message queue → Data → Agentic (logged) → user interface (valve shown as updated). One loop from sensing to decision to execution is complete.

This six-step flow runs smoothly thanks to one structured datum running through it all: the **point value (PointValue)**. Every data report and every command dispatch carries a `PointValue` with semantic labels, unit, timestamp, and tenant ID. Agentic's LLM can read the meaning of a moisture value and target the right device when switching a valve. Without this layer of normalization, what passes among the five centers would be a pile of meaningless raw bytes.

When deploying the five centers' collaboration in the field, the table below lists common problems and recommended practices, for reference during architecture reviews and system tuning.

| 1 | Which center owns device authentication? | Route uniformly through Gateway to Auth; store no sensitive credentials on the device side |
