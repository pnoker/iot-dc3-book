# 《万物智联》写作指南

本文件是全书写作规范的唯一来源，供作者、编辑和辅助写作的 Agent 共同遵循。篇章结构以 `book/config/parts.yaml` 为准，图表字段和配色以 `book/config/style.yaml` 为准；本文件不重复维护这些机器配置。

## 1. 定位与读者

本书以“从连接到智能”为主线，系统讲解物联网平台如何从设备接入、通信和数据处理，演进到 AIoT 与智能体应用。

目标读者包括：

- 希望系统理解物联网技术体系的软件与架构工程师；
- 负责设备接入、平台建设、数据处理或智能运维的研发人员；
- 希望理解 AI Agent 如何安全接入物理世界的 AI 应用开发者；
- 具备基本编程和计算机网络知识的高校师生及技术管理者。

内容应兼顾原理和工程实践。不要写成概念百科、产品宣传册或只针对某个开源项目的使用手册。

## 2. 全书主线

三篇内容各有明确边界：

- 基础篇解释物联网平台的底座，包括体系架构、感知、通信、平台和数据处理；
- 技术篇解释平台如何获得软件工程、AIoT、智能体、安全及标准化能力；
- 应用篇解释通用方法如何落到工业、城市、农业和可信协作等场景，并以项目实战收束。

IoT DC3 是贯穿部分章节的工程案例，不是所有结论的唯一依据。讲解时先说明通用问题、标准和方法，再用 IoT DC3 或其他案例展示实现取舍。除项目实战章节外，不把项目模块介绍替代技术论证。

## 3. 技术边界

涉及 AI 与物理设备时必须保持以下边界：

- 设备接入、稳定采集和可信数据是 AI 能力的前提；
- LLM 适合理解意图、归纳信息、辅助分析和编排受控工具，不替代确定性控制逻辑；
- 高风险写操作必须经过鉴权、参数校验、策略约束、审计和必要的人工确认；
- 实时控制、安全联锁和故障保护应由 PLC、边缘控制器或其他确定性系统承担；
- MCP 用于连接 AI 应用与工具、资源或提示上下文，不替代 MQTT、CoAP、Modbus 等设备通信协议；
- 不把“模型能够调用工具”表述为“模型可以无条件控制设备”。

介绍方案时同时说明适用条件、代价、失败方式和降级路径，避免只写理想流程。

## 4. 语言与术语

采用准确、克制、面向工程实践的技术出版语言：

- 先说结论或问题，再展开原因和实现，不堆砌口号；
- 避免“颠覆”“赋能”“万能”“零成本”等营销化或绝对化表达；
- 中文语句使用中文标点，代码标识符、命令、协议名和 API 名保持原文；
- 专有术语首次出现时使用“中文名（English Name，缩写）”，后文统一使用中文名或缩写；
- 已有公认中文译名时优先采用，无法准确翻译时保留英文并解释含义；
- 同一概念全书使用同一称呼，不随意混用“节点/设备”“属性/测点”等近义词；
- 一个段落集中表达一个核心观点，避免连续过长句和无层次的名词罗列。

类比可以帮助理解，但必须在类比后回到准确的技术定义，不用类比代替机制说明。

## 5. 章节组织

章节和小节优先采用以下展开顺序，可按内容需要删减，不机械套用：

1. 以真实问题、场景或矛盾说明为什么需要这项技术；
2. 给出概念、组成和工作机制；
3. 说明关键数据流、控制流或交互流程；
4. 分析选型条件、工程权衡、限制和安全风险；
5. 用标准、通用架构或真实项目案例落地；
6. 用小结、检查表或决策要点收束。

章节之间应有自然衔接。引用前后章节时使用 `parts.yaml` 中的正式章节名称，并检查编号是否仍然有效。

## 6. 代码、命令与表格

- 代码只用于证明关键机制，避免粘贴与主题无关的完整工程；
- 示例应能独立理解，明确运行环境、输入、输出和省略部分；
- 使用带语言标识的 fenced code block；命令使用 `bash`，配置按实际格式使用 `yaml`、`json` 等；
- 不在示例中出现真实密钥、密码、Token、内网地址或个人数据；
- 版本相关 API 必须核对当前官方文档，不凭记忆编写；
- 表格用于结构化比较，列名应表达比较维度，单元格避免塞入大段正文；
- 性能数据必须说明测试条件、时间和来源，不能把单次测试写成普遍结论。

## 7. 图表

需要展示组件关系、时序、数据流、层次或选型矩阵时优先使用图表，不用装饰性图片替代信息表达。

图表按 `book/config/style.yaml` 定义的 `book-figure` 规格编写：

- `type` 必须属于 `allowed_types`；
- `required_fields` 中的字段必须存在且非空；
- `legend` 仅在颜色、线型或符号无法自解释时提供；
- `elements` 描述图中实体，`relationships` 描述实体间有方向和含义的关系；
- `caption` 应独立说明图表结论，而不是只复述标题；
- `render_notes` 说明布局、强调层级和打印可读性；
- 颜色以 `style.yaml` 的 `palette` 为权威来源，不自行维护另一套色值。

图表必须在灰度打印、缩放和脱离上下文时仍可辨认，不能只依赖颜色区分语义。

## 8. 事实与时效性

以下内容在写入或修改时必须查阅最新的一手资料：

- 标准的正式名称、版本、状态和发布组织；
- 框架、SDK、协议扩展和云服务的版本与 API；
- 市场规模、设备数量、性能指标和安全事件；
- 仍在快速演进的 AI Agent、MCP 和模型能力边界。

优先使用标准组织、官方文档、规范原文、论文和项目官方仓库。无法确认的信息应缩小表述范围或明确时间点，不用模糊措辞掩盖不确定性。

## 9. 交稿检查

完成章节或小节后检查：

- 是否服务于本章标题和全书主线；
- 是否区分通用方法、标准要求和具体项目实现；
- 是否解释了适用条件、代价、风险和降级路径；
- 术语、章节编号、代码和图表引用是否一致；
- 易过时事实是否核对了一手资料并标明时间范围；
- AI 控制物理设备的表述是否包含权限、安全和确定性边界；
- 是否存在营销化、绝对化、重复或无法验证的结论；
- 新增 `book-figure` 是否满足 `style.yaml` 的字段和类型约束；
- 修改篇章结构后是否同步检查目录、导读和跨章节引用。
