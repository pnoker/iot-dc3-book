### 6.3.2 设备数据采集与协议适配层实现

采集层是物联网平台对外部世界的“耳朵”，职责明确：接收设备上报的原始报文，完成协议解析、数据完整性校验、单位换算，最终将统一格式的设备数据写入缓存并交付消息队列。它不关心业务规则，不处理告警阈值，只负责把异构的现场数据变成平台可消费的标准化值。设计不当，采集层会成为全系统最早崩溃的瓶颈。

#### 数据采集的核心矛盾

平台层只认识统一格式的位号值（位标识符、时间戳、数值、质量戳），而现场设备交上来的是各类协议封装。MQTT Broker 拿到的是保留 Topic 下的 JSON Payload，Modbus 采集器收到的是 16 进制寄存器列表，OPC UA 客户端读到的是带命名空间的数据变量节点。把这些形状各异的字节流转化为统一的数据模型，是采集层要解决的第一个问题。

第二个问题是吞吐与可靠性的平衡。大批量设备高频上报时，数据点吞吐量可达数百万次/秒量级。如果每个数据点都单独写入消息队列，时序库的写入压力会急剧上升。解决方案是短周期批量聚合——不是逐条发送，而是按时间窗口汇总后再投递。

#### 适配器模式与分层职责

IoT DC3 的采集层（即 Driver 模块组）用适配器模式（Adapter Pattern）解耦协议差异。每个协议对应一个独立的 Driver 服务，对外暴露统一的接口，对内封装协议特定的编解码逻辑。

示意 Java 伪代码结构如下（假设场景）：

分层后三个组件的职责：

- **接口层**：定义 `DeviceDriver` 接口，声明初始化、读写和销毁生命周期。南北向均依赖该接口编程。
- **适配层**：每个协议的 Driver 实现类只干一件事——将该协议的数据模型翻译为 `PointValue`（设备 ID + 位号标识符 + 数值 + 质量戳 + 时间戳）。MQTT Driver 解析 JSON Payload，Modbus Driver 解析寄存器字节序，OPC UA Driver 读取节点 Attribute。
- **会话层**：全局唯一的 `ConnectionManager` 管理所有活跃连接，负责连接池、重连、心跳保活。断线重连策略必须精确配置——每分钟重试 1 次，连续 3 次失败后进入指数退避（1 分钟、5 分钟、15 分钟），直到人工重置或定时复位。

#### 缓存设计：设备影子与两级缓存

协议解析后的数据不直接发送到消息队列，而是先写入两级缓存。

- **一级缓存**：Caffeine 本地缓存（Java 进程内）。保存每个设备的最新位号值，即“设备影子”（Device Shadow）。Caffeine 支持基于时间和基于权重的淘汰策略，配置写延迟和读延迟为亚秒级，容量覆盖最近一段时间内所有活跃设备的最新值。
- **二级缓存**：Redis 分布式缓存。保存设备影子供其他中心服务（设备管理、告警引擎）跨进程查询。Caffeine 作为写缓冲区周期性向 Redis 同步，同步粒度是增量更新——只推送发生过变化的数据点，不刷全量。

这么设计的取舍：Caffeine 是进程内缓存，减少了对 Redis 的即时访问压力，但也引入了数据不一致窗口（数秒级）。对于采集频率高但查询实时性要求不苛刻的场景（如环境监控），这个窗口可接受。对于秒级告警场景，则必须走 Redis 直读或降低同步周期。

#### 批量调度与吞吐优化

批量调度器按固定短时间窗口（如数秒）从 Caffeine 缓存中一次性提取“本次窗口内新增或更新的数据点”，将清单按设备 ID 重组为批量消息体，然后投递到 RabbitMQ 或 Kafka。每条批量消息包含若干设备的所有位号值变化记录，终端消费者按设备 ID 逐一拆包处理。

不同协议下的配置建议（示意）：

| 协议 | 典型数据频率 | 推荐缓存 TTL | 批量窗口 | 序列化方式 |
|--------|----------|----------|------|-------|
| MQTT  | 按事件变化上报 | 60 秒 | 2 秒 | Protobuf / JSON |
| Modbus | 定时轮询 (数秒) | 30 秒 | 3 秒 | Protobuf |
| OPC UA | 订阅模式 | 120 秒 | 5 秒 | Protobuf |

#### 串口采集场景：遍历器模式

对于非 TCP/IP 的串口设备（RS-232 / RS-485），不存在“设备主动上报”，而是采集器主动发起轮询。DC3 的 Driver 用遍历器模式（Iterator Pattern）解决：`CollectionIterator` 依次遍历设备列表，每台设备完成寄存器读取、数据拼包后，交付协议解析器解码为 `PointValue`，然后写入缓存。遍历间隔由驱动配置控制（假设数百毫秒）。该模式下批量调度器同样起作用——多次遍历的累积数据仍由窗口调度器统一投递。

采集层是平台上线后改动成本最高的模块——协议适配、缓存配置、批量窗口均需根据现场场景反复调试才能稳定。参数调优建议在生产前使用压测工具（如 Eclipse Kura 或自写 JUnit Driver 基准）做一次完整评估，再落地到生产配置中心。
