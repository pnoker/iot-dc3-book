### 6.2.3 服务发现、配置管理与API网关

微服务拆分后，三个基础问题立刻摆到桌面上：服务A如何找到服务B的动态地址？配置参数改了，几十个实例怎么同步生效？外部客户端应该访问哪个统一入口？这三个问题分别由服务发现（Service Discovery）、配置管理（Configuration Management）和API网关（API Gateway）解决。它们不承载业务逻辑，但缺了任何一个，微服务架构都无法稳定运转。

#### 服务注册与发现：让服务彼此可见

单体应用里方法调用依赖编译时的固定地址。微服务部署后，实例IP和端口动态分配——Kubernetes重启一个Pod，地址就变了。服务发现维护一张“活地图”：每个服务启动时向注册中心登记地址和健康状态，下线时自动注销；调用方从注册中心按服务名查询地址，无需硬编码。

注册中心的选择取决于一致性需求、运维能力和生态集成。下表列出几个主流选项，对比基于通用工程实践，非基准测试。

**表6-2 服务发现组件对比（示意性对比）**

| 特性 | Nacos | Eureka | Consul | ZooKeeper |
|------|-------|--------|--------|-----------|
| 一致性模型 | AP+CP（可切换） | AP（最终一致性） | CP（强一致性） | CP（强一致性） |
| 健康检查 | 心跳+主动探活 | 心跳 | 健康脚本+gRPC | 心跳 |
| 配置管理 | 原生支持 | 需整合Spring Cloud Config | 原生支持（Key-Value） | 不自带 |
| 服务发现协议 | HTTP/gRPC | HTTP | HTTP/gRPC | TCP |
| 适用规模 | 大规模部署 | 规模适中后优势减弱 | 大规模部署 | 大规模部署 |
| Spring Cloud集成 | 原生对齐 | 维护模式 | 需额外适配 | 需额外适配 |
| 运维复杂度 | 低 | 低 | 中等 | 高 |

组件选型受生态影响很大。假设一个团队使用Spring Cloud生态，Nacos可以同时扛起服务发现和配置管理两个角色，运维负担低。Eureka虽然成熟，但新项目不推荐再使用（示意性判断）。Consul更适合需要强一致性的基础设施服务，但适配Spring需要额外工作。ZooKeeper更基础，适合对强一致性有要求的场景，但运维复杂度高。

以Nacos为例描述典型注册流程（假设场景）：设备管理微服务的两个实例分别运行在两台主机上，端口均为8080。启动时向Nacos注册，之后按配置间隔发送心跳。数据采集微服务查询设备快照时，从Nacos拉取服务列表，通过负载均衡调用其中一个实例。这个过程对业务代码透明——只需在Spring Boot应用上添加`@EnableDiscoveryClient`注解。

#### 集中配置管理与动态刷新

物联网系统的配置项多且容易变化：采集周期、告警阈值、Broker地址、数据库连接串。每次改配置都重启实例，生产环境无法接受。配置管理的目标是“集中存储、实时生效”。

Spring Cloud Config可以把配置源存放在Git仓库，而Nacos通过控制台或API直接管理。以Nacos为例（假设场景）：运维人员在Web界面上创建配置项并为服务绑定。当需要临时降低某条产线的采集频率以节省带宽，只需在Nacos页面上修改对应参数并发布。服务端立即推送变更事件，业务代码在字段上加上`@RefreshScope`注解即可自动注入新值，全程零重启。这种能力对物联网动态分组、规则更新非常实用。

#### API网关：统一入口与路由

如果客户端直接调用微服务，会面临跨域、认证、限流、日志、协议转换等问题。每个服务各自实现一套既重复又容易遗漏。API网关作为系统唯一的北向入口，统一处理这些横切关注点，再把请求路由到对应的后端服务。

Spring Cloud Gateway是构建API网关的常见选择。以下YAML配置定义了两条路由规则。第一条将`/api/device/**`的请求转发到名为`dc3-device-manager`的服务，并附带过滤器用于校验JWT令牌。第二条将WebSocket连接路由到`dc3-driver`服务。

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: device-manager-route
          uri: lb://dc3-device-manager
          predicates:
            - Path=/api/**
          filters:
            - name: TokenCheck
              args:
                excludePaths: /api/login,/api/register

        - id: driver-websocket-route
          uri: lb:ws://dc3-driver
          predicates:
            - Path=/ws/**
          filters:
            - StripPrefix=1
```

`lb://`前缀告诉网关使用负载均衡客户端，从注册中心（如Nacos）动态获取实例列表。请求处理顺序为：匹配Predicates → 执行过滤器链（鉴权、限流、日志） → 转发给下游服务。这种动态路由在服务实例扩缩容时无需改动网关配置。

#### 边缘网关与云端网关的分工

上述API网关主要运行在数据中心或云上，管理南北向流量（设备↔应用↔外部服务）。但物联网场景中，如果全部流量都经过云端网关，会浪费带宽、增加延迟。实践中需要分层：**边缘网关（Edge Gateway）** 部署在设备侧，负责协议转换（如Modbus RTU转MQTT）、数据预处理（过滤无效值、统计计算）、本地缓存和离线续传。**云端网关**（如Spring Cloud Gateway）负责认证、路由、服务限流、API版本管理等。边缘网关把处理后的干净数据推送至云端，一次上报携带多个位号值，而非每个传感器单独发消息，显著降低网络负载。例如在一个工厂场景（假设场景）中，多台PLC通过Modbus TCP连接到边缘网关，边缘网关汇总后按固定间隔只推送一条包含所有位号值的MQTT消息到云端，避免逐条上报带来的网络拥塞。

服务发现解决“找得到”的问题，配置管理解决“改得快”的问题，API网关解决“进得来”的问题。这三个组件构成了微服务基础设施的三根立柱。实践中，选择Nacos一个组件即可覆盖注册中心和配置中心的双重角色；API网关统一承担安全、限流和路由职责。在大规模部署时，还需区分边缘网关与云端网关的分工，避免所有流量直接冲入云端，确保系统具有伸缩性和低延迟。关于微服务架构下如何进一步将AI能力（如智能告警、预测性维护）集成到基础设施中，将在第7章详述。
