### 9.5.2 MCP协议消息格式与能力描述

要填平AI意图与设备指令之间的语义鸿沟，上一节提到的“上下文”不能凭空存在，它需要一种标准化的载体。MCP的核心设计之一，就是在这套载体内清楚地回答两个问题：交互时该带什么信息，以及设备能做什么。如果说传统协议是一张只写了“收件人”和“内容”的明信片，MCP则是一份装有简历、便签和任务单的文件夹。

#### 消息结构：三层信封

MCP没有另起炉灶发明二进制协议，而是选择JSON作为基础格式。理由很直接：JSON对AI系统的解析引擎友好，也便于与上游云服务、Webhook对接。一条MCP消息分为三层，从上到下分别是控制面、语义面和执行面：

1. **消息头**：包含消息ID（UUID格式）、时间戳、协议版本号、源和目标端点标识。这一层负责路由和去重，与MQTT的固定头功能类似，但不承载业务语义。

2. **上下文段**：这是MCP区别于传统协议的关键。它不是普通的载荷或元数据，而是一个结构化的上下文数据块，携带当前会话的历史状态、环境标签（如`"room":"living"`、`"mode":"night"`）、上次交互结果摘要以及用户偏好画像的快照。AI侧处理新请求时可直接读取此段，不必回溯全部会话日志，这就解决了上一节提到的“传统协议无状态”问题。上下文段可以增量更新：每次交互后，Broker或设备只追加变化的部分，避免重复传输整段历史，降低带宽开销。

3. **动作段**：具体要执行的操作或请求的设备数据。对AI Agent发出的指令，这里是意图描述；对设备回复，这里是执行结果或状态快照。动作段内部保持结构化，允许嵌套子动作和错误码。

三层结构的设计，让中间节点（如MCP Broker或智能网关）无需解析动作细节就能完成路由和上下文缓存——它只需读消息头判断去向、读上下文段判断是否需要更新快照。这种职责分离是MCP让AI系统和设备网络解耦的工程基础。

#### 能力描述：设备功能的统一“简历”

如果说消息结构是MCP的信封，能力描述（Capability Descriptor）就是设备投递给AI系统的“个人简历”。它采用JSON格式，让AI能够自动解析并加入工具列表。以下是IoT DC3中MCP实现所定义的能力描述示例（资料：[S5]），该示例描述了一盏可调光智能灯的完整能力：

```json
// 假设场景/示意：MCP设备能力描述（Capability Descriptor）示例
{
  "protocol": "mcp-v1",
  "device-id": "light-living-room-01",
  "device-type": "urn:mcp:device:light",
  "profile": {
    "manufacturer": "示例灯业",
    "model": "DimmerPro-X"
  },
  "context-info": {
    "supported-labels": ["mode:night", "mode:party", "scene:welcome"],
    "retain-history": true
  },
  "actions": [
    {
      "name": "setBrightness",
      "description": "设置灯光亮度",
      "input": {
        "type": "object",
        "properties": {
          "brightness": {
            "type": "integer",
            "minimum": 0,
            "maximum": 100,
            "unit": "percent",
            "semantic-tags": ["saref:OnOffState", "saref:Level"]
          }
        },
        "required": ["brightness"]
      },
      "constraints": [
        "firmware_upgrade_in_progress: this action is blocked"
      ]
    },
    {
      "name": "setColor",
      "description": "设置灯光颜色",
      "input": {
        "type": "object",
        "properties": {
          "color": {
            "type": "string",
            "format": "hex-color",
            "semantic-tags": ["ssn:Property", "iot:ColorProperty"]
          }
        },
        "required": ["color"]
      },
      "constraints": []
    }
  ],
  "properties": {
    "currentBrightness": {
      "type": "integer",
      "semantic-tags": ["saref:OnOffState", "saref:Level"]
    },
    "powerState": {
      "type": "string",
      "enum": ["on", "off"],
      "semantic-tags": ["saref:OnOffState"]
    }
  }
}
```

这份能力描述有几个关键设计点：
- **设备类型**（`device-type`）和**动作**（`actions`）定义了设备边界和能力清单，AI Agent据此决定是否调用。
- **输入参数**中的`semantic-tags`字段，引用了现成的本体，如SAREF（Smart Applications REFerence）和SSN（Semantic Sensor Network）。AI不需要硬编码“brightness就是亮度”，而是通过标签关联到通用知识库，在语义层面理解这个属性。
- **约束**（`constraints`）字段描述设备在特定条件下不可用的操作。传统设备往往等到执行报错时才告诉客户端“当前无法执行”，而MCP让设备在一开始就声明约束条件，AI可以在行动前预判是否可行。例如，约束`firmware_upgrade_in_progress: this action is blocked`告诉AI：如果设备当前处于固件升级状态，亮度调节操作会被拒绝。更复杂的约束还可以用布尔表达式组合多个条件，例如`"device_motion_sensor_disabled || battery_low"`，供AI决策引擎做逻辑推理。

#### 与W3C WoT Thing Description的关系

MCP能力描述在概念上借鉴了W3C的Web of Things Thing Description（WoT TD）。WoT TD是更广义的“万物描述”标准，而MCP的能力描述是AI场景下的一个特定子集和微调，侧重于**动作的可执行性**、**上下文的连续性**和**语义标签的可推导性**。一个符合W3C WoT TD标准的设备，可以通过一个适配器对外暴露为MCP能力描述。换言之，MCP能力描述相当于一个剪裁过的、更适合AI Agent动态调用的WoT TD Profile。它去掉了WoT TD中面向Web界面和人类开发者的部分，强化了面向AI自动解析和执行的部分。例如，WoT TD中的`forms`字段用于定义具体协议绑定（HTTP、CoAP等），MCP能力描述中将其抽象成`protocol`字段，统一声明为“mcp-v1”，底层传输由MCP Broker根据上下文段自动协商。这种设计使设备在描述能力时无需关心底层通信细节，专注于自身功能。

#### AI Agent查询指令

当AI Agent决定使用这盏灯时，它发出的不是固定的MQTT主题`light/set`，而是一个结构化的MCP消息。动作段的核心是一个意图描述，而不是底层实现细节：

```json
// 假设场景/示意：AI Agent发起的MCP查询指令（动作段）
{
  "intent": {
    "name": "setBrightness",
    "parameters": {
      "brightness": 75,
      "context-label": "mode:night"
    }
  },
  "sync": true,
  "timeout": 5000
}
```

AI Agent告诉MCP网络：我要执行`setBrightness`，参数亮度75，并告知设备当前处于“夜间模式”。设备不需要知道AI如何理解用户的自然语言指令，只需解析自己能力描述中已经登记过的`setBrightness`动作即可。AI与设备之间的翻译工作，由MCP的消息格式和能力描述共同完成。如果设备收到这条指令时处于固件升级状态，它会根据约束条件返回一个`ActionBlocked`错误，并在错误码中明确原因。

#### 工程注意点一览

| 关键要素 | 设计意图 | 常见陷阱 |
| --- | --- | --- |
| 三层信封结构 | 分离路由信息、语义上下文与具体动作，便于中间件按需缓存和处理 | 将上下文段塞入动作段导致上下文丢失或解析混乱，违背解耦初衷 |
| 语义标签（`semantic-tags`） | 使AI能跨设备类型理解属性，而非依赖命名约定 | 标签引用已废弃或未经维护的私有命名空间，导致解析失败 |
| 约束字段 | 允许设备在特定条件下拒绝执行，避免误操作和物理损坏 | 约束描述过于模糊（如“视情况而定”）或使用自然语言，AI无法预判；应当使用标准化表示 |
| 上下文段历史保留 | 让AI在多轮交互中保持连贯理解 | 为减少带宽而裁剪掉关键历史片段，导致AI上下文断裂 |

能力描述的设计，本质上是把设备从“执行器”提升为“可对话的参与者”。它们不再是只知道0和1的机器，而是能告诉AI“我会什么、怎么做、什么情况下不能做”的智能实体。这为下一节要展开的语义互操作——不同制造商的设备如何在AI的调度下协同工作——铺平了道路。
