### 3.5.2 边缘节点上的数据预处理与过滤

硬件选型只是解决了“在哪算”的问题。接下来要回答的是“算什么”。一个边缘节点可能同时接入几十路传感器——温度、湿度、振动、电流、气压。如果每个传感器每秒钟产生的原始读数都原封不动地往云端推，网络带宽很快就会被占满，而且大部分数据对业务没有任何价值。一台振动传感器每秒采集5kHz的加速度数据，平台真正需要分析的只是停机前那几秒的异常波动。更棘手的是，很多保护性动作要求毫秒级的响应——等数据传到云端、触发规则、再下发指令，现场可能已经出了事故。

边缘节点上的数据预处理，核心任务可以归结为三个方面：**滤波去噪、数据聚合、异常判定**。这三步做扎实之后，上行数据量通常能压缩到原始流量的十分之一甚至更低，而本地动作的响应延迟可以从秒级降到采样周期级别。

#### 滤波去噪：从混乱中提取干净信号

来源：本书示例场景，相关数值用于说明工程判断，非通用统计结论。
传感器采集到的原始信号几乎不可能纯净。电源纹波会在模拟信号上叠加50Hz或100Hz的周期性干扰；电磁耦合会引入高频毛刺；机械振动可能导致非接触式传感器的读数来回跳动。一个温度传感器，如果直接拿单次读数去判断是否超限，很可能因为一个50ms的电压毛刺而触发误报警——风机关了又开，车间温度根本没到边界值。

边缘节点上最常用的去噪手段是**滑动平均滤波（Moving Average Filter）**。它维护一个固定长度的环形缓冲区，每收到一个新采样值就替换掉缓冲区中最旧的那个，然后重新计算所有值的算术平均，把这个均值作为当前输出。窗口的长度决定了滤波的“惯性”——窗口越长，平滑效果越强，但对真实变化的跟踪延迟也越大。工程师需要根据信号的变化速度和系统对响应延迟的要求来调节这个参数。比如，对于变化缓慢的室温（以分钟为单位变化），窗口长度设到几十个采样周期都没问题；但对于需要快速检测冲击的加速度信号，窗口超过十个采样点就可能把一次冲击特征抹平。

**代码清单3-2：滑动平均滤波实现示例（假设场景）**

```c
// 滑动平均滤波 - 假设场景，数值仅为示意
#define WINDOW_SIZE 5

float buffer[WINDOW_SIZE] = {0};
uint8_t index = 0;
uint8_t count = 0;
float sum = 0;

float moving_average_filter(float new_sample) {
    if (count == WINDOW_SIZE) {
        sum -= buffer[index];
    }
    buffer[index] = new_sample;
    sum += new_sample;
    index = (index + 1) % WINDOW_SIZE;
    if (count < WINDOW_SIZE) {
        count++;
    }
    return sum / count;
}

// 伪代码调用示意（假设场景）
// float raw_temp = read_temperature_sensor();
// float filtered_temp = moving_average_filter(raw_temp);
// if (filtered_temp > 45.0f) {
//     trigger_local_alarm();
//     send_mqtt_event("temperature_alert", filtered_temp);
// }
```

滑动平均不是唯一的滤波器。如果噪声的频谱比较固定且不与信号频谱重叠，用一阶或二阶无限脉冲响应（Infinite Impulse Response, IIR）低通滤波器效果更好，运算量也极低。如果数据中偶尔出现幅值极大的野点（比如因电磁脉冲导致的瞬时跳变），中值滤波更合适——它取窗口内的中位数，对单个异常点不敏感。在MCU算力受限的节点上，一个调好窗口长度的滑动平均往往比一个IIR滤波器更可靠，因为后者对浮点精度的要求更高，容易在定点MCU上出现数值漂移。

#### 数据聚合：向上传结果，而非样本

滤波输出的是干净的连续数值流，但对上层平台来说，大多数时候它不需要每一条记录。边缘节点可以在一个时间窗口内对多个采样值进行聚合计算，只上传最能代表该窗口状态的几个统计量。常见的聚合操作包括算术平均、最大值、最小值、峰值、累积积分值。

假设一个环境监测节点每秒采集一次温度数据，而平台每5分钟才需要一次平均温度来做能效分析。节点可以在5分钟窗口内累积300个采样值，算出均值，只向平台推送一条记录。这样上行数据量从每分钟60条降到0.2条——压缩了将近两个数量级。同理，在电机电流监测场景中，边缘节点可以在一个工频周期（20毫秒）内计算电流的有效值和峰值，只上传这两个特征值，而不是全波形的几千个采样点。

不适用的场景也有：如果上层需要对原始波形做精细分析（例如振动频谱或声纹），就不能在边缘层压缩掉时域细节。但这恰恰是边缘节点扩展能力的切入点——在本地做快速傅里叶变换（Fast Fourier Transform, FFT），只上传频谱特征矢量或几个主要频段的幅值。既保留了与故障相关的频域信息，又把传输量压缩到原始数据的千分之一量级。

#### 异常检测与本地决策

滤波和聚合降低了数据量，但边缘节点的真正价值在于**可以独立于云平台做出快速响应**。常见的做法是在节点上预设阈值规则：当处理后的数据触发阈值时，节点立即执行本地动作——驱动继电器、输出PWM控制信号、发送本地声光告警，同时将异常事件打上时间戳后上传给云平台做持久化与分析。

再次用环境监测的假设场景来说明：节点监测车间温度，滑动平均滤波后的值如果连续3次超过45°C，节点立即通过GPIO输出高电平驱动风扇继电器，同时通过MQTT向平台发送一条带标记的事件消息。从传感器读数异常到风扇启动，整个过程在三个采样周期加滑动窗口的延迟内完成——大约5秒左右（假设采样周期1秒）。这个延迟远低于上传云平台再等待指令下发的往返时间（在较好的网络条件下也需要几百毫秒，在网络拥塞时可能达到数秒或超时）。

这种本地闭环还有一个重要的工程价值：网络断开时，节点仍能独立完成保护性控制。网络恢复后，缓存在非易失存储器中的事件数据再补传到云端。这在工业现场和偏远监测站点中尤为关键——不会因为一次网络抖动就导致设备失控。

#### 工程权衡：边缘干多少才算够

在边缘节点上做预处理不是越多越好。每增加一个处理环节，就多一层代码复杂度和算力消耗，也可能引入新的故障点。一个实用的经验准则是：**只在边缘执行“无需上下文”的操作**。滤波、去噪、格式转换、单点阈值判断——这些只依赖当前读数或短窗口内的历史值，不需要跨设备的数据比对或长时间序列的统计规律。需要趋势预测、多传感器联合分析、大数据量建模的任务，应该留给边缘网关或云平台来处理。

边缘节点上的预处理为感知层增加了一道数据质量门槛，也开启了本地快速闭环的能力。本节的滤波、聚合、异常检测，都是围绕着“清洁数据”和“快速响应”这两个核心目标展开的。下一节会把预处理的能力再推进一步——不再依赖人工预设的固定阈值，而是让边缘节点在端侧学会自己区分正常与异常，这就是端侧人工智能（TinyML）要解决的核心问题。
