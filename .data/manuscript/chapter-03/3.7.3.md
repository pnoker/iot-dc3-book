### 3.7.3 物模型在数据互通中的实践

上一节为温度传感器定义了一份针对单一型号的物模型。实际项目中，很少有只用一种传感器的情况。A 厂的温湿度变送器走 Modbus RTU，温度数据放在第 3–4 字节，以十六进制表示；B 厂的空调控制器用 KNX 总线，温度设定值对应一个通讯对象号；C 厂的智能电表遵循 DL/T645 规约，数据标识符一套接一套。每对接一个新品牌，应用开发团队就要学习它的私有协议、编写解析代码、反复调试位号映射。物模型要解决的核心问题，正是这套“异构数据归一”。

图 3-7-3-1 揭示了物模型在数据互通中三个关键的工程机制。

**语义适配层消弭协议鸿沟。** 物模型将设备能力抽象为位号、指令、事件三类能力，这与 W3C Web of Things Thing Description 规范中对设备能力的分类逻辑相似。A 厂传感器用十六进制输出“01 0A”，适配层将高字节转为十进制并乘以 0.1，得到 10.0℃；B 厂空调的 KNX 数据点“9.001”表示的也是标准浮点温度值。通过物模型，这两者的“温度”属性归入同一个位号。上层应用读温度值时，不需要知道原始数据来自 Modbus 寄存器、KNX 通讯对象还是 DL/T645 数据标识符。这个适配过程通常由边缘网关或硬件抽象层一次性实现，后续同品牌设备接入只要走相同的协议映射，无需重复编码。

**设备影子拆解同步耦合。** 物联网设备常有离线时刻——低功耗节点大部分时间休眠，或者现场网络抖动导致连接断开。如果每次下发指令都要等待设备在线，业务流程会被拖死。图 3-7-3-1 中虚线框标注的设备影子就是缓冲区：平台持有设备的最新物模型状态，应用层对影子的某个属性（如“设定温度”）进行写操作，影子记录期望值；设备下次上线时主动拉取影子中的期望值，与当前状态对比，发现差异就执行同步。写操作不再被设备在线状况阻塞。

**物模型催生平台无关的应用开发。** 假设开发一套楼宇能源优化策略，它需要知道每层空调的送风温度。如果所有空调遵循同一物模型，这套策略在甲楼宇的 BACnet 环境、乙写字楼的 Modbus 现场、丙工厂的自定义总线中都能直接复用——开发时只依赖物模型的位号和指令，不关心设备品牌或总线类型。业务逻辑与基础设施彻底解耦，这是实现应用代码一次编写、多处部署的前提。

来源：本书示例场景，相关数值用于说明工程判断，非通用统计结论。
用一个示意流程可以更直观地看到物模型如何工作：温度传感器上报原始报文 → 边缘网关上的物模型适配器解析出“温度=25.3℃，湿度=60.2%RH”并更新设备影子 → 云平台的应用通过同一物模型读取影子中的位号值。整个过程应用不接触任何私有通信细节，实现了从感知层到应用层的统一数据模型。

在 IoT DC3 平台中，物模型通过位置 `/profile` 系列的 REST API 进行管理，设计上遵循一个设备归属一个物模型、多个同型号设备复用同一个物模型的原则。平台将适配层逻辑集成到设备接入模块中。来自感知层的数据流一路带着清晰的语义标签向上传递——实时监控面板、告警规则、能源报表都能在这个统一的语义空间里直接对话，不需要为每个厂商的私有格式单独处理。
