### 13.2.1 基于DID的设备身份设计方案

传统物联网身份管理的基本形态是：设备出厂时烧录对称密钥或X.509证书，接入平台时通过中心化认证服器的校验。这个模式在单一平台内工作良好，但设备一旦需要跨组织交换数据——比如一台车载温湿度传感器同时向物流系统和交通管理系统上报数据——那个中心化注册表就成了瓶颈和单点故障。设备若想更换平台，需重新烧录身份；数据接收方也无法独立验证设备本身，只能信任颁发证书的平台。

去中心化标识符（Decentralized Identifier, DID）提供了一条不同的路径。DID的设计思路是让标识符不由单一注册机构管理，而由标识符的**主体**——设备本身或它的合法控制者——自主生成和控制。一个DID的字符串结构形如 `did:<method-name>:<method-specific-id>`，比如 `did:example:abcd1234`，其中`example`是DID方法，`abcd1234`是该方法域下的唯一标识。DID的核心价值不在于字符串本身，而在解析它之后得到的**DID文档**。这份结构化数据（通常为JSON-LD格式）包含当前有效的公钥列表、服务端点以及认证协议。它回答了验证方的问题：“声称是这台设备的家伙，该用哪把公钥核实它的签名？”（[W3C DID Core标准](https://www.w3.org/TR/did-core/)定义了DID的核心数据模型和操作语义。）

将这套方案部署到物联网设备上，需要逐一解决三个工程环节：密钥与硬件的物理绑定、DID文档上链与更新、以及设备丢失或私钥泄露后的撤销。

**密钥与设备绑定：物理锚定。** 信任根必须从代码迁移到硬件。具体做法是，每台设备在出厂阶段，于板载**安全飞地**（Secure Enclave）中生成一对非对称密钥。这块物理隔离的安全元件，密钥一旦生成就不可导出，只允许通过接口调用签名或解密操作。不少物联网硬件厂商选用具备低成本安全芯片的器件（假设场景，例如采用类似工业级安全芯片的器件）来存储椭圆曲线密钥并执行ECDSA签名。主控MCU只持有公钥，从未触碰私钥。即使攻击者通过物理手段提取MCU固件，也无法获取签名私钥。更高安全等级的场景——如智能电表、工业控制器这类需合规认证的设备——可使用可信平台模块（Trusted Platform Module, TPM）。设备据此构造自己的DID：常见做法是用公钥的SHA-256哈希作为DID中的`method-specific-id`。一台设备的DID因此在物理层面绑定到了它的硬件密钥，而不是一个可被复制或转移的软件文件。

工程权衡上，选择安全飞地需平衡成本与防护等级。大批量消费级设备（如智能灯泡）对成本敏感，允许私钥在安全芯片中存活但可能无法抵御侧信道攻击；工业级设备（如医疗输液泵）则需要更高等级认证的专用安全元件。这是身份管理的根本工程判断：防护等级与部署成本之间必须找到一个可接受的平衡点。

**注册与更新：上链声明。** 设备生成DID后，需要将DID文档写入区块链。注册操作的实质是：向智能合约提交一笔由设备私钥签名的交易，合约验证签名后，将该DID和对应文档的哈希存入链上状态。关键约束是：只有持有当前私钥的控制者才能更新该DID对应的公钥或服务端点。这点与PKI模式不同——PKI中证书续期依赖CA中心；而DID模式中，更新权在设备所有者手中，不再需要上级机构批准。下面的Solidity代码展示了一个简化合约，实现注册、验证和吊销三个最小功能集：

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.21;

contract DeviceDIDRegistry {
    struct DIDDocument {
        address owner;          // 控制该DID的链上地址
        bytes32 publicKeyHash;  // 公钥哈希（实际可用公钥本身，此处用哈希缩减存储）
        uint256 timestamp;      // 注册或最后更新时间戳
        bool isActive;          // 是否有效
    }

    mapping(bytes32 => DIDDocument) private didDocs;  // DID哈希 -> 文档

    event DIDRegistered(bytes32 indexed didHash, address indexed owner, uint256 timestamp);
    event DIDUpdated(bytes32 indexed didHash, address indexed owner, uint256 timestamp);
    event DIDRevoked(bytes32 indexed didHash, uint256 timestamp);

    // 注册：用DID和公钥哈希注册一台设备
    function registerDevice(string calldata _did, bytes32 _publicKeyHash) external {
        bytes32 didHash = keccak256(bytes(_did));
        require(didDocs[didHash].timestamp == 0, "DID already registered");
        didDocs[didHash] = DIDDocument({
            owner: msg.sender,
            publicKeyHash: _publicKeyHash,
            timestamp: block.timestamp,
            isActive: true
        });
        emit DIDRegistered(didHash, msg.sender, block.timestamp);
    }

    // 验证：给定DID和消息哈希，验证ecrecover恢复出的地址是否与控制者匹配
    function verifySignature(
        string calldata _did, bytes32 _messageHash,
        uint8 _v, bytes32 _r, bytes32 _s
    ) external view returns (bool) {
        bytes32 didHash = keccak256(bytes(_did));
        DIDDocument storage doc = didDocs[didHash];
        require(doc.isActive, "Device is not active");
        address signer = ecrecover(_messageHash, _v, _r, _s);
        return (signer == doc.owner);
    }

    // 吊销：仅设备所有者可操作
    function revokeDevice(string calldata _did) external {
        bytes32 didHash = keccak256(bytes(_did));
        require(didDocs[didHash].owner == msg.sender, "Not the owner");
        didDocs[didHash].isActive = false;
        emit DIDRevoked(didHash, block.timestamp);
    }
}
```

这个合约抓住身份管理的最小操作集。每次注册记录一个链上地址作为owner，`verifySignature`利用Solidity的`ecrecover`从签名中恢复签名地址，与owner比对。这隐含了一个工程前提：设备必须能组织合法的以太坊格式交易，或生成能被ecrecover验证的离线签名。实际部署中，完整DID文档（含公钥、服务端点）通常托管在IPFS等链下存储，链上只保留IPFS哈希与文档指针，以降低存储成本。

对应一个关键工程检查点：
- **密钥生成**：确保安全飞地中生成的密钥不可被主控MCU导出。
- **DID构造**：确认`method-specific-id`的哈希算法与合约中的`keccak256`（Ethereum标准）一致。
- **交易签名**：验证设备离线签名的交易格式能被`ecrecover`正确解析。
- **链上状态**：检查`isActive`字段在注册、更新后始终为`true`。
- **链下存储**：确认DID文档的IPFS哈希与链上指针匹配。

**撤销与失效：链上原子操作。** PKI中证书吊销最棘手：CRL和OCSP需要额外检查层，且存在从吊销请求提交到全网感知的延迟窗口。DID的撤销更直接：控制者调用`revokeDevice`，合约将`isActive`置为false。一旦区块链打包确认，所有同步该账本的节点都能即时看到吊销状态。但有一工程约束：位于深井或隧道中的电池供电传感器，可能几小时甚至几天才与链同步一次。缓解做法是——在握手中加入“最大允许时间戳差”。验证方在DID文档活跃的基础上，额外要求本次通信的签名时间戳与最新区块时间相差不超过N个区块。这项措施在PKI中同样存在，但DID将吊销的时间控制权从中心CA移到了设备所有者手中，丢失私钥时可立即“断电”。

此外，若设备被物理破坏，私钥虽未泄露但设备无法再发起签名交易。此时需要预先设置“继承者”或“恢复密钥”。典型做法是注册时指定一个备用公钥地址（例如工厂管理密钥），该密钥有权在出示“设备死亡证明”（例如连续N个时间周期无心跳）后执行吊销。这个设计增加了链上逻辑的复杂性，在简约合约中通常省略，实际产品中值得纳入。

DID方案带来的核心转变是信任源头的迁移：从信任中心化注册表，转向**信任区块链的状态一致性 + 设备硬件安全飞地的物理锚定**。代价也很明显——设备需要具备签名能力，链上交互会消耗gas费用，电池供电的轻节点设备难以维持与链的实时连接。工程常见的折中策略是：设备在本地用离线批次签名（例如累计10条消息后生成一枚聚合签名），再交由边缘网关代为提交上链，以此降低频率与成本。这个模式呼应了13.1.3节提到的“阶段二：轻节点部分上链”——信任全节点代为转发，但设备依然保有身份控制权和签名私钥的物理独占权。
