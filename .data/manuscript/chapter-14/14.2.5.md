### 14.2.5 AI运维功能实现

前一節完成了设备数据从接入到落库的全链路：MQTT.fx 上报 JSON 负载 → EMQX Broker → RabbitMQ → 数据中心解析 → MongoDB/TDengine。数据落库之后的问题是：从海量时序数据中自动发现异常，并在设备故障前发出预警。这正是 AI 运维填补的空隙。

IoT DC3 在体系架构中定义了智能中心作为 AI 能力的入口。第7章已拆解过自然语言运维和 Agent 编排层面的设计，本小节聚焦更底层的执行链路：**如何将一台设备的温度、振动、电流时序数据，经过训练好的模型，变成一条可被规则引擎消费的告警事件**。

#### 从规则到统计，再到模型

很多团队一谈“AI运维”就想到深度学习模型，这是认知上的跳跃。更稳妥的路径是分三档走：

第一档是**固定阈值**。例如温度超过设备手册规定的上限，或电流超过额定值的某个百分比，直接触发告警。实现简单，但无法适应负载变化和季节漂移。第二档是**统计方法**。基于滑动窗口计算均值、标准差，用四分位数距离（IQR）或 Z-score 判定离群点。在一个假设场景中，某工厂风机在正常工况下的振动标准差稳定在 ±2Hz 级，负载变化时均值从20Hz漂到30Hz，但 Z-score 仍落在 ±3 以内；一旦轴承开始磨损，标准差上升明显，Z-score 超过4，触发告警。第三档才是**有监督或无监督模型**，用于识别复杂模式，比如多传感器的联合异常或早期退化趋势。

IoT DC3 的规则引擎本身就可以消费第一档和第二档的输出。当需要进入第三档时，才需要在智能中心引入模型推理服务。三种方式不是替代关系：阈值规则处理明确红线，统计方法覆盖缓慢漂移，模型捕捉机器已学习到的复合特征。在一个生产级部署中，三者通常并存，并以优先级链的方式串联：先过阈值，再过统计，最后送入模型。

#### 预测性维护模型训练示意

假设场景：手头有一台离心泵的历史数据集，包含过去12个月的传感器记录：入口压力、出口压力、流量、电机电流、轴承振动、壳体温度，以及每次停机维护的时间戳和故障原因。目标是训练一个模型，能够根据最近 N 个时间步的传感器读数，输出轴承退化概率。

在训练阶段，模型结构不需要复杂——一个两层的 LSTM 加上 Dense 输出层，输入长度为32的时间窗口，输出为二分类概率：

```python
# Python 异常检测模型训练脚本（假设场景/示意）
import numpy as np
import tensorflow as tf
from tensorflow.keras.models import Sequential
from tensorflow.keras.layers import LSTM, Dense, Dropout

# 假设 data 是形状为 (样本数, 32, 6) 的 NumPy 数组
# labels 是形状为 (样本数,) 的 0/1 标签
data = np.random.randn(5000, 32, 6)
labels = np.random.randint(0, 2, (5000,))

model = Sequential([
    LSTM(64, return_sequences=True, input_shape=(32, 6)),
    Dropout(0.2),
    LSTM(32),
    Dropout(0.2),
    Dense(16, activation='relu'),
    Dense(1, activation='sigmoid')
])

model.compile(optimizer='adam', loss='binary_crossentropy', metrics=['accuracy'])
model.fit(data, labels, epochs=50, batch_size=64, validation_split=0.2)

# 保存模型
model.save('pump_bearing_anomaly.h5')
```

这个片段不是生产级代码——真实场景中需要处理缺失值、时间戳对齐、类别不平衡（故障样本远少于正常样本）、滑动窗口的步长与重叠策略。但它展示了核心链路：原始时序 → 窗口化 → 深度学习 → 保存模型 → 导出部署。

#### 模型微服务化部署：TensorFlow Serving

训练完成后，模型文件（`.h5` 或 SavedModel 格式）需要被部署为可被调用的微服务。TensorFlow Serving 是实践中最成熟的选择之一：它提供一个 gRPC/REST 端点，接收序列化的请求，返回推理结果，并支持热加载模型版本。

```dockerfile
# 假设场景/示意：TensorFlow Serving Docker 配置
FROM tensorflow/serving:2.12.0
COPY pump_bearing_anomaly /models/pump_bearing_anomaly/1
ENV MODEL_NAME=pump_bearing_anomaly
```

启动后，推理端点通过 REST 调用即可接入 IoT DC3 的智能中心。智能中心订阅数据中心经 RabbitMQ 推送的实时位号值，组合成窗口数据后，向 TF Serving 发起推理请求，返回的概率值再写回数据中心，或直接触发告警规则。

这是一个关键的设计选择：**推理结果本身就是一个“衍生位号”**。在物模型中，温度、压力是原始位号，`bearing_anomaly_score` 则是智能计算位号。它跟普通传感器值一样可以被规则引擎处理——如果分数超过0.85且持续超过5个采样周期，则生成一条“P级告警”事件写入告警表。这样，AI 能力的输出完全复用平台的规则层和通知层，不需要单独再建一套告警管道。

#### 模型与规则引擎的联动边界

不是所有异常都要走 AI。固定阈值能解决的，不需要模型；统计方法能覆盖的缓慢趋势，也不需要深度学习。AI 模型适合的场景有三个特征：**多变量耦合**（单看温度和压力都不异常，但两者联动的模式异常）、**时间依赖性**（前序行为决定当前状态）、**模式复杂**（难以用阈值或线性统计描述）。

在 IoT DC3 中，这个联动由智能中心的 Agent 编排来完成。Agent 订阅实时数据流，触发推理任务，并将结果写回标准数据管道。规则引擎始终是“最终的告警判断者”——它不关心源头是物理传感器还是 AI 模型，只负责比较位号值与告警规则。这让系统保持了分层清晰：AI 提供新输入，但不跳过已有治理逻辑。

将模型推理结果视作衍生位号的处理方式，是整个 AI 运维实现中最值得记住的工程判断。它避免了 AI 系统成为平台的一座孤岛，而是成为数据链路上的另一个生产者——与设备、网关、边缘计算节点平级。后续的告警、可视化、报表、自动决策，全部复用已有管道，不需要为新能力重写一遍平台。

#### AI 运维的安全边界

部署 AI 模型推理服务时，必须考虑三类安全风险。第一，**输入投毒**：恶意构造的传感器数据可能诱导模型给出偏差预测。至少应在智能中心入参前执行数据格式校验、合法值域过滤和异常值截断（如将 NaN/Inf 拒绝或替换为默认值）。第二，**模型劫持**：未认证的请求可能消耗推理资源或探测模型行为。TF Serving 端点应配置 API 密钥或使用服务网格的 mTLS 进行访问控制，并限制每设备每秒推理请求次数。第三，**输出泄露**：衍生位号本身可能反映设备工况秘密（如运行状态、退化规律）。应基于设备管理的角色权限，仅允许授权用户或服务消费 AI 推理结果。在 IoT DC3 中，智能中心通过 OAuth 2.1 和 RBAC（基于角色的访问控制）统一管理推理调用方权限，衍生位号的写入与读取同样遵循租户隔离策略。这些措施构成了 AI 运维的底线——智能不能以牺牲安全为代价。
