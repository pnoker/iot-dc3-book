### 14.2.4 设备接入与数据流

前一小节打通了设备注册、数据上报、告警触发的主链路，但那条链路的入口是 Netty 实现的 TCP 服务。实际项目中，设备接入的方式远不止一种——MQTT（Message Queuing Telemetry Transport，消息队列遥测传输）因为对弱网环境更友好、社区生态成熟，往往是首选的“南向协议”。本小节以 MQTT 接入为例，展示一条从设备端经 Broker 到数据中心再落到数据库的完整数据流，并覆盖数据格式选择与可视化集成的工程判断。

#### 模拟设备接入：MQTT 客户端工具的角色

在开发阶段，用一个真实的硬件设备反复调试既低效又不可控。更常见的做法是用 MQTT 客户端工具（如 MQTTX 或命令行工具 mosquitto_pub）模拟设备行为。这类工具允许你手动配置 Broker 地址、端口、Client ID、Topic，并以指定 QoS 发布或订阅消息。

假设场景：IoT DC3 平台已部署并启动，Broker 使用开源实现（如 EMQX 或 Mosquitto）。在客户端工具中填入 Broker 地址（假设为 `192.168.1.100:1883`），Client ID 设置为设备的注册标识（如 `device-001`），连接成功后订阅平台下发命令的 Topic（例如 `dc3/command/device-001`），然后向设备数据上报 Topic（例如 `dc3/data/device-001/upload`）发布 JSON（JavaScript Object Notation，JavaScript 对象表示法）格式的属性数据。这一步验证了设备与 Broker 之间的 TCP 连接是否正常、Topic 路由是否正确。

这里有一个容易被忽视的细节：Client ID 必须在同一个 Broker 实例下唯一，否则后连接的那个会踢掉前者。IoT DC3 的设备凭证生成逻辑会确保每个设备获得唯一的 Client ID 或 Username/Password 组合。

#### 数据格式：JSON 还是 Protobuf

设备上报的数据需要序列化成字节流。JSON 和 Protobuf（Protocol Buffers，协议缓冲区）是最常见的两种选择，取舍点如下：

| 维度 | JSON | Protobuf |
|------|------|----------|
| 可读性 | 人类可读，调试友好 | 二进制，需 schema 才能解析 |
| 带宽消耗 | 文本冗余，Payload 较大 | 紧凑，适合低带宽或高频采集 |
| 解析性能 | 字符串解析，性能中等 | 预编译，性能高 |
| 平台兼容 | 几乎所有语言原生支持 | 需要生成桩代码 |
| 变更成本 | 加字段不影响旧解析器（向前兼容需约定） | schema 变更需同步更新桩代码 |

在实际项目中，**B端设备资产密集、带宽费用敏感的场景更倾向 Protobuf**；而**C端智能家居或中小型项目，JSON 的开发效率高、调试成本低，往往被优先采用**。大多数物联网平台默认支持 JSON 格式，同时提供协议扩展接口，允许开发者注册自己的编解码器。

设备属性上报的典型 JSON 结构如下：

```json
{
  "deviceId": "device-001",
  "timestamp": 1700000000123,
  "properties": {
    "temperature": 25.6,
    "humidity": 68.2,
    "pressure": 1013.25
  },
  "event": "periodic"
}
```

字段说明：
- `deviceId`：平台注册时下发的设备唯一标识。
- `timestamp`：Unix 毫秒时间戳，建议由设备端打上（云端收到后可能重写，但保留原始戳用于去重或时延分析）。
- `properties`：属性-值键值对，物模型定义中每个属性有数据类型和取值范围（参见第3章“物模型抽象”）。
- `event`：可选字段，标示该数据是周期性上报、告警触发还是响应命令。

**关键工程判断**：消息队列（MQ）是 IoT 数据流的“稳压器”。设备上报速率可能极不均匀——白天生产高峰时每秒上千条，夜间几乎为零。如果数据接入服务直接写入数据库，数据库连接池很容易被冲垮。MQ 起到了削峰填谷和异步解耦的作用，同时允许处理服务按自身能力消费。IoT DC3 采用的 RabbitMQ 处理常规吞吐量足够，但在百万级设备场景下应考虑 Kafka，后者在日志场景的持久化和高吞吐上更有优势。

#### 数据查询与可视化集成

数据落库后，业务侧需要查看历史趋势、实时数值、设备状态。IoT DC3 对外提供 RESTful API，支持按设备 ID、时间范围、属性名查询时序数据。可视化层可以对接 Grafana，通过 InfluxDB 数据源配置仪表盘，也可以使用平台自带的 Web 控制台（基于 Vue.js + ECharts）。

可视化集成步骤大致如下：
1. 确认 Grafana 版本 ≥ 8.0，安装 InfluxDB 数据源。
2. 配置查询语句，例如 `SELECT "temperature" FROM "autogen"."device_metric" WHERE "deviceId" = 'device-001' AND time > now() - 1h`。
3. 将结果展示为折线图或表格，设置告警阈值（如温度超过 50°C 触发钉钉通知）。

至此，一条从设备端发送，经过 Broker、MQ、处理服务、数据库，最终映入可视化面板的数据流已完整成型。这个闭环往往是物联网项目可行性的“信心枢纽”——当你看到第一个数据点在仪表盘上跳动时，整个架构才算真正跑通。
