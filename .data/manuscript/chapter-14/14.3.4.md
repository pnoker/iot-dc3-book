### 14.3.4 团队协作与文档

物联网项目的组织维度，往往比技术实现更棘手。一个典型的物联网团队至少包含四类角色：做传感器与硬件的电子工程师、写嵌入式代码的固件工程师、构建平台后端与API的软件工程师，以及处理数据与模型的算法工程师。这四组人的知识背景、交付节奏、开发工具、甚至术语体系都不同。一个稍微复杂的设定反馈——比如“设备上报时间戳精度不够导致时序数据乱序”——就可能让四方在沟通会上争论半小时。

跨学科团队的协作效率，最终落在文档和协议上。下面几点是实践中最容易补齐、也最容易被忽视的环节。

**接口文档规范：OpenAPI 用于北向，设备模型用于南向。** 平台层对外暴露的 RESTful API 应当用 OpenAPI 规范（原 Swagger）描述（资料：[S10]）。这不是为了生成漂亮的文档页面，而是为了让前端、移动端、业务系统和第三方集成方能快速理解请求与响应结构，并由工具自动生成客户端 SDK。这一点多数后端团队已经做到。但物联网平台的南向接口——即设备与平台之间的通信协议——往往缺乏类似的规范。设备上报的数据结构通常以 JSON 或 Protobuf 形式定义，但如果没有一个版本化的、跨团队可引用的“设备物模型”文档，固件工程师改了一个字段名，平台后端就可能在解析时静默丢弃数据。工程判断：南向和北向的接口文档应当保持同一规范级别，前者用物模型定义（包含属性、事件、命令、数据类型与枚举值），后者用 OpenAPI 规范，两者在 CI/CD 流程中接受自动校验。

**设备通讯协议文档：作为跨团队契约。** 设备连接层使用的通信协议（MQTT 主题定义、CoAP 资源路径、Modbus 寄存器映射）应当独立成一份版本化的文档，由固件团队与平台团队共同维护，并在每次修改时触发变更通知。一个常见陷阱是：固件工程师在固件中改了 MQTT 主题命名，但没有更新文档，平台团队在下一个 Sprint 才发现数据接入失败。为避免这类问题，推荐将协议定义以 YAML 或 JSON 格式存储于代码仓库，在 CI 管道中将协议文件转换为可读文档发布，同时生成代码桩用于集成测试。这样协议变更在版本管理中可追踪，耦合团队的开发节奏也能对齐。

**设计文档与架构决策记录。** 物联网项目涉及大量跨层决策：为什么选择 MQTT QoS 1 而非 QoS 2、为什么设备认证采用 X.509 而不是预共享密钥、为什么数据持久化选择时序数据库而非关系数据库。这些决策在立项时只是在白板上讨论过，几个月后新成员加入时，团队需要重新推演一遍。轻量级架构决策记录（Architecture Decision Record, ADR）是解决这个问题的实用工具。ADR 通常是一两页的 Markdown 文件，记录决策背景、考虑过的选项、最终选择及其权衡。它不是厚厚的架构说明书，而是随项目演进的决策日志。每次做了涉及跨团队职责边界的决策，就写一份 ADR，合并到代码仓库的 `docs/adr/` 目录下。这样当有人问“为什么这里用 Kafka 而不是 RabbitMQ”时，答案已在版本历史里，不用靠回忆。

**版本管理与变更通知。** 物联网项目的版本管理比纯软件项目复杂——固件版本、驱动版本、平台服务版本、协议版本各有各的节奏，且它们之间存在依赖关系。一个为团队带来显著的效率提升的做法是：建立一个版本兼容矩阵（Compatibility Matrix），在每次发布时明确标注“平台版本 X.Y.z 支持的固件版本范围”“协议版本 v2 向下兼容 v1 吗”。变更通知则依托 CI/CD 管道的自动发布通知或内部分发渠道，确保硬件团队、测试团队和运维团队都能在变更到达前知道影响范围。

延伸阅读：OpenAPI 规范可从 openapi.org 获取最新版本和工具集；架构决策记录的轻量级模版可以在 `architecture-decision-record` 网站上找到推荐格式。如果你是团队的技术负责人，在上述四类文档中，建议优先补上设备通讯协议文档和 ADR 记录——这两项在大多数物联网团队的文档成熟度评估中是最薄弱的环节。
