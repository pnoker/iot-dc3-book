### 14.4.2 工程收束与工程检查表

从需求分析到架构取舍，从代码实现到部署运维，再到 AGI 时代的架构预判——本章走完了一个物联网平台从零到交付的全生命周期。但方法论的价值不在于被“知道”，而在于被“执行”。这一节没有新的论述，只有一份可以直接拿到项目会上用的检查表。

**工程检查表：物联网项目关键阶段自查项**

这份表以项目推进顺序组织，每个阶段核心逻辑为：输入工件 → 关键决策 → 输出件。适合项目经理、技术负责人和架构师在里程碑评审时逐项核对。

**一、项目启动与需求阶段**

- [ ] 是否已识别所有利益相关方（设备厂商、运维团队、业务方、最终用户）？
- [ ] 是否区分了连接管理需求与数据消费需求？是否需要物模型 Thing Model抽象？（参考第2章、第3章）
- [ ] 非功能需求清单是否包含：并发设备数、最大吞吐、上行/下行延迟要求、离线缓存窗口、数据保留周期？
- [ ] 是否使用 MoSCoW 方法（Must/Should/Could/Won't）明确了第一版发布范围的优先级？
- [ ] 是否明确物联网业务问题，而非简单用技术方案替代？例如问题应是“停电后恢复流程”，而非“开发 OTA 功能”。
- [ ] 安全需求是否已包含最低基线：设备身份认证、传输层加密、最小权限？（参考第8章、第9章。资料：[S7]）
- [ ] 输出件：用例目录 + 功能设计（轻量级 RFP 级别） + 非功能需求表。（参考第7章 Enterprise IoT 设计方法）

**二、架构设计阶段**

- [ ] 采用分层架构（设备层 → 边缘层/接入层 → 平台层 → 业务层/智能层）且每层职责清晰，无误层调用。
- [ ] 南向协议接入是否通过统一的驱动或适配器封装？是否预留了边缘下沉扩展点？（参考第14.2.2节。资料：[S8]）
- [ ] 消息队列选型是否符合场景？（低频高可靠 -> RabbitMQ；高通量日志 -> Kafka。）
- [ ] 微服务划分依据业务边界，而非技术堆栈。如“设备管理”、“规则引擎”为独立服务。
- [ ] 时序数据库选型是否匹配数据写入模型（高频写入、冷热分离、降采样策略）？
- [ ] 是否定义标准物模型（属性、事件、服务）？API 版本管理策略？
- [ ] 边云协同的异步解耦层是否已明确？（参考第14.1.2节。资料：[S8]）
- [ ] 输出件：系统架构图（包含所有关键组件与数据流）、技术选型决策记录（ADR）。

**三、开发实现阶段**

- [ ] 是否搭建了 CI/CD 管道？单元测试、集成测试、端到端测试覆盖率是否明确？（参考第14.1.3节）
- [ ] 设备模拟器是否就位？是否覆盖了典型场景（正常上报、离线重连、异常包、批量注册）？
- [ ] 下行指令（远程配置、OTA、设备重启）是否经过安全校验（Token/签名）？
- [ ] 规则引擎是否支持灰度发布？是否具备运行时热加载能力？
- [ ] 是否预留了产品级的配置管理？（环境变量 → 配置中心）
- [ ] 代码是否包含故障注入测试能力（如网络延迟、服务熔断）？
- [ ] 输出件：可部署的微服务镜像、接口文档、告警规则配置文件。

**四、部署与上线阶段**

- [ ] 选择何种部署形态：全手动 / Docker Compose / Kubernetes ？（参考第14.1.4和第14.2.6节。资料：[S1]）
- [ ] 是否已完成可观测性栈（Prometheus + Grafana + ELK日志+分布式链路追踪）的集成？
- [ ] 是否已配置基础告警（服务宕机、消息队列积压、CPU/内存超阈值、错误率上升）？
- [ ] 设备接入的域名/TLS证书是否配置完毕？是否正确使用了通配符证书？
- [ ] 是否进行过容量估算（假设场景：预期1000台设备，每秒100条消息）和压力测试？
- [ ] 回滚/降级策略是否已测试？（驱动与MQ断开时，云侧服务应优雅降级，而非雪崩。）
- [ ] 安全基线清单是否已执行：默认密码修改、非必要端口关闭、RBAC权限模型部署？（资料：[S7]）
- [ ] 输出件：部署拓扑图 + 运维手册（含故障排查标准流程）+ 上一节已完成的安全清单。

**五、运维与迭代阶段**

- [ ] 是否有明确的版本迭代流程及变更通知机制？（如：OSS公告、邮件列表、Slack频道）
- [ ] 是否采集过线上日志并复盘过“第一次生产故障”？根因是否已纳入知识库？
- [ ] 模型/规则是否有观察-验证-更新的闭环流程？
- [ ] 是否定期（如每季度/每半年）进行安全审计和依赖库升级？
- [ ] 是否收集并整合了用户（运维人员与设备使用者）的深度反馈，用于下一轮迭代？
- [ ] 团队新人通过现有文档能否在1-2个工作日内启动并加入开发？如果不能，文档需要补充。

**常见陷阱速查表**

| 陷阱            | 如何发生 | 如何排查 | 如何避免 |
|----------------|----------|----------|----------|
| MQTT 丢消息      | QoS=0且网络抖动 | 检查Broker日志：设备是否重连 | 关键指令使用QoS=1/2（第14.3.1节） |
| 时序数据库膨胀    | 未做降采样/冷热分离 | 监控存储增速 | 定义保留策略与降采样规则 |
| 上行数据反压设备  | 云侧处理慢，TCP窗口填满 | 查看MQ消费积压 | 异步解耦+设备端sendTimeout |
| 服务发现配置错   | Nacos注册失败 | 检查网关访问日志，看路由是否生效 | 统一配置中心+健康检查 |
| 弱口令导致设备被控| 保留出厂密码 | 扫描内网设备，尝试弱口令 | 强制首次登录修改密码 |

**延伸阅读推荐**

- **工程方法论深化**：重读本书第1-2章，形成“连接 → 智能”的业务认知框架；关注 Enterprise IoT 领域关于解决方案生命周期（Solution Lifecycle）的设计方法，即“计划 → 构建 → 运行”的完整闭环（资料：[S3]）。
- **代码实战参考**：若想从零搭建另一版本，可参考 Maque IotHub 项目的实现结构（资料：[S2][S5]），MQTT 协议的深入解析和 CoAP 集成的核心要点（资料：[S12]）。
- **架构安全基线**：本书第8章（安全技术）、第9章（协议标准）可作为长期参考，每次架构升级前建议快速过一遍，确保不遗漏关键点。生产部署前，务必阅读 IoT DC3 官方安全策略和运维清单（资料：[S1][S7]）。
- **AGI 与 IoT 结合前沿**：持续关注 AI 编排与设备自治的结合。当“端侧模型”和“云端大模型”真正实现低成本、低时延的融合时，本章提及的架构演进将从实验性走向产品化。

这份检查表不是死规矩，而是一个对话起点。每个项目都有它独特的约束——预算、工期、团队能力、技术债——列出的每一项都值得问一句：“这个检查点在我们的上下文里，优先级是 Must 还是 Should？” 能回答这个问题，就说明你已经从“照着做”走到了“理解做”。
